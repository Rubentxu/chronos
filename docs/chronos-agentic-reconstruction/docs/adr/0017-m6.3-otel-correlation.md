# ADR-0017 — M6.3 correlación no ambigua con evidencia de mutaciones

**Status:** Accepted
**Date:** 2026-09-21
**Cycle:** M6 / M6.3 (correlación no ambigua con evidencia de mutaciones)
**chronos HEAD:** `d7773965` (post M6.2 alignment).
**Spike location:** off-repo, `/home/rubentxu/.jcode/scratch/m6.3-otel-correlation/`.

## 1. Context

ROADMAP §M6 §86 lists M6.3 as "correlación no ambigua con
evidencia de mutaciones". The requirement is twofold:

1. **No ambiguity** — for every chronos event, there is
   exactly ONE correlation to a `RecordedInvocation` (one
   `InvocationId`, optionally one external `trace_id`). No
   event has two or more competing correlations.

2. **Mutation evidence** — when a state mutation occurs
   (an event changes chronos state, e.g., a session field
   flips), the before/after pair **shares** the same
   correlation. Mutations never cross invocation
   boundaries.

This ADR delivers a `CorrelationStore` that:

- Binds events by index (no per-event UUID needed; the
  stream itself provides ordering).
- Stores `bindings: HashMap<u64, RecordedInvocation>` for
  the 1:1 event → correlation map.
- Stores `by_trace: HashMap<Vec<u8>, Vec<u64>>` for
  cross-correlation queries by external trace_id.
- Stores `by_invocation: HashMap<Uuid, Vec<u64>>` for
  cross-correlation queries by InvocationId.
- Stores `mutations: HashMap<u64, (u64, u64)>` for the
  before/after pair, queryable by either event_idx.

The store is the M6.3 deliverable. The contract:

- `bind(event_idx, rec)` is the only way to add a binding.
  Idempotent: re-binding the same event_idx replaces the
  previous binding (no silent multi-binding).
- `record_mutation(before_idx, after_idx)` records the
  pair. Both events are recorded as part of the pair.
- `mutation_is_correlated(before, after)` returns
  `Ok(true)` only if both events have the SAME
  `RecordedInvocation`; `Ok(false)` if they have
  different ones; `Err(EventNotBound)` if either is
  unbound.

## 2. Decision

**Accepted.** The correlation store is a single struct with
4 hash maps and 5 ingestion methods:

```rust
pub struct CorrelationStore { ... }

impl CorrelationStore {
    pub fn bind(&mut self, event_idx: u64, rec: &RecordedInvocation);
    pub fn record_mutation(&mut self, before_idx: u64, after_idx: u64);
    pub fn lookup(&self, event_idx: u64) -> Option<&RecordedInvocation>;
    pub fn events_for_invocation(&self, inv: InvocationId) -> Vec<u64>;
    pub fn events_for_trace(&self, trace_id: &TraceId) -> Vec<u64>;
    pub fn mutation_of(&self, event_idx: u64) -> Option<(u64, u64)>;
    pub fn bound_count(&self) -> usize;
    pub fn trace_count(&self) -> usize;
    pub fn invocation_count(&self) -> usize;
}

pub fn ingest_stream(
    store: &mut CorrelationStore,
    rec: &RecordedInvocation,
    events: &[ChronosEvent],
) -> usize;

pub fn ingest_mutations(
    store: &mut CorrelationStore,
    stream_start: u64,
    mutations: &[(u64, u64)],
) -> usize;

pub fn mutation_is_correlated(
    store: &CorrelationStore,
    before_idx: u64,
    after_idx: u64,
) -> Result<bool, CorrelationError>;

pub fn unambiguous_correlation(
    store: &CorrelationStore,
    event_idx: u64,
) -> Result<&RecordedInvocation, CorrelationError>;

pub fn count_unambiguous(
    store: &CorrelationStore,
    event_count: u64,
) -> (u64, u64, u64);
```

### 2.1 ChronosEvent is decoupled from correlation

`ChronosEvent` does **NOT** carry correlation info. The
event has `ts_micros`, `probe`, and `fields` — but no
`invocation_id`, no `traceparent`. Correlation is
**inferred** by the store, not embedded in the event.

Why: events are produced by the runtime (e.g., probe
callbacks in chronos-core). Embedding correlation would
require every event producer to know about correlation. By
keeping events decoupled, the producer stays focused on
the observation, and the correlation store (a separate
component) does the bookkeeping.

### 2.2 Mutation pair invariant

The M6.3 invariant: **a mutation pair always binds to the
same `RecordedInvocation`**. The `mutation_is_correlated`
check enforces this by `PartialEq`-comparing the two
`RecordedInvocation`s. If they differ, the mutation is
detected as crossing an invocation boundary — a violation
that the calling code must handle.

This invariant is what M6.3 means by "evidencia de
mutaciones": the **evidence** is the `Record<String>` that
the pair has the same correlation. Without this check,
mutations could silently split invocations and lose
correlatability.

### 2.3 Event field typing

`ChronosEvent` has typed fields, not a stringly-typed
blob. `EventField` is an enum with 4 variants:

```rust
pub enum EventField {
    Str(String),
    Int(i64),
    Bool(bool),
    DomainRef(String),
}
```

`DomainRef` is for chronos-domain entity references (a
session ID, a tool name, etc.) — distinguishable from
arbitrary user strings. This prevents the field values
from being mis-parsed as IDs or vice versa.

## 3. Wire format (chronos-domain event stream)

The spike does NOT define a wire format — events are
internal to chronos-core and consumed by the correlation
store directly. (Wire format for OTel export is M6.4.)

The internal event struct is:

```rust
pub struct ChronosEvent {
    pub ts_micros: u64,
    pub probe: String,
    pub fields: Vec<(String, EventField)>,
}
```

Fields are key/value pairs, keys are probe-specific
strings, values are typed (`EventField` enum). The store
does not interpret fields; it only binds the event to a
correlation.

## 4. Behavioural spec

### 4.1 Binding rules

- `bind(event_idx, rec)` inserts the binding. If
  `event_idx` is already bound, the previous binding is
  **replaced** (not multi-bound). This is the "no
  ambiguity" enforcement: an event has exactly one
  correlation.
- `bindings` is a `HashMap<u64, RecordedInvocation>` — by
  construction, 1:1.
- The store also indexes `by_trace` and `by_invocation`
  for cross-correlation queries. These are **derived** from
  the bindings; no separate `bind_to_trace` API exists.

### 4.2 Mutation rules

- `record_mutation(before_idx, after_idx)` inserts
  `(before_idx, after_idx)` keyed by **both** `before_idx`
  and `after_idx`. So `mutation_of(before_idx)` and
  `mutation_of(after_idx)` both return `Some((before,
  after))`.
- A mutation is NOT bound to a RecordedInvocation
  directly; instead, the store **checks** at query time
  that both events share a RecordedInvocation. This keeps
  mutation evidence separate from binding.
- `mutation_is_correlated` uses `PartialEq` on
  `RecordedInvocation`. Two bindings are "the same" iff
  their `InvocationId` and `ExternalTraceContext` (if
  any) match byte-exact.

### 4.3 No ambiguity enforcement

- `unambiguous_correlation(event_idx)` returns
  `Err(EventNotBound)` if the event isn't bound. There is
  no `unambiguous_or_default` — ambiguity or unbound is
  surfaced, never silently defaulted.
- `count_unambiguous(event_count)` returns
  `(unambiguous, ambiguous, unbound)`. In this spike, the
  "ambiguous" counter is always 0 (binding is 1:1). The
  slot exists for future multi-binding scenarios (e.g.,
  a fan-out where one event correlates to N invocations).

### 4.4 Cross-correlation invariants

- `events_for_invocation(inv)` returns event indices in
  insertion order (HashMap<Vec<u64>> insertion order, not
  sorted).
- `events_for_trace(trace_id)` returns event indices in
  insertion order.
- Distinct `RecordedInvocation`s produce distinct
  `trace_count()` and `invocation_count()` — never
  double-counted.

## 6. Why this matters for M6

M6.3 closes the **correlation bookkeeping** that the rest
of M6 builds on:

- **M6.4 (exporter)** consumes the correlation store to
  emit OTel spans. Each span carries the
  `RecordedInvocation` for the events it's exporting.
- **M6.5 (security/redaction)** uses
  `events_for_invocation` to find all events for a
  redacted session; the correlation makes redaction
  total without losing trace context.
- **M6.6 (UAT)** spins two services; the correlation
  store proves the cross-service events share an
  invocation when they should.
- **M6.7 (gates)** verifies that round-trip
  `ingest → bind → query` preserves correlation:
  `count_unambiguous` must equal the input event count.

## 7. Out-of-scope / future work

- **No event IDs**. The store uses indices into a stream,
  not UUIDs. A production version should add UUIDs (or
  domain IDs) for events that survive across streams.
- **No persistence**. The store is in-memory only.
  Production should add a persistence layer
  (chronos-store already has one — integration belongs
  to CapCorrelationPersistence).
- **No streaming/append-only API**. `bind` and
  `record_mutation` are imperative. A log-structured
  API (append-only operations) would simplify crash
  recovery.
- **No event field schema**. Fields are
  `Vec<(String, EventField)>` — untyped at the key level.
  A typed event schema (probe → field types) would be
  M4R.3-style overlay on top of M6.3.
- **No correlation to dataflows**. The store correlates
  events to invocations; not to dataflow dependencies.
  Dataflow correlation is M9 (causal concurrency).
- **No automatic mutation detection**. Mutations are
  declared explicitly via `record_mutation`. A future
  cycle could add automatic detection (diff before/after
  events).

## 10. Closing note

**M6 §M6.3 is delivered.** The `CorrelationStore` proves
that every event has a single, unambiguous correlation
and that mutations preserve correlation. The store is
queriable by both internal `InvocationId` and external
`trace_id`, with 16/16 cargo tests passing in 0.0 s.

The spike is **path-dep** on M6.1 and M6.2 (both off-repo
at `$JCODE_SCRATCH_DIR`). It can be lifted into
chronos-core as a submodule when the M6 chapter begins
productisation. The store contract — `bind`, `lookup`,
`mutation_is_correlated`, `events_for_invocation`,
`events_for_trace` — is what M6.4, M6.5, M6.6, and M6.7
will all consume.
