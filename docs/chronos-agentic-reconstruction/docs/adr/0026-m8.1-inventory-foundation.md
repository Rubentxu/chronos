# ADR-0026 — M8.1 inventario del foundation histórico de shrinking (M8 chapter already CLOSED in `main`)

**Cycle:** M8 / M8.1 (counterexample shrinking y test intelligence — preservación + inventario del foundation histórico)
**Status:** `verified` post-write (docs-only; no code change; no merge required, branch HEAD == `main @ 55c68e4e`)

## 1. Context

ROADMAP §M8 §81 — "M8.1 preservar e inventariar el foundation histórico de shrinking; M8.2 runner/proptest/Hypothesis con id de experimento, entradas y seed; M8.3 rerun determinista y predicado invariante; M8.4 reducción + slice causal; M8.5 CLI `chronos test` como spike, si aporta valor; M8.6 UAT-M8-01/02. No confundir con CONC-001 (M9)."

Al inspeccionar `main @ 55c68e4e` antes de comenzar M8.1 — siguiendo §0.1 del orquestador SDDK (revalidar HEAD + repo state) — se descubre que el capítulo M8 **ya está CLOSED** en `main` y no solo en `origin/main`. La expectativa inicial era construir M8 desde cero (6 sub-ciclos), pero el grafo Git muestra:

- **6 tags `m8-0X-*.0`** (m8-01 a m8-06) firmando cada merge de sub-cycle.
- **7 milestones** en `docs/milestones/` (m8-01..m8-07 + M8-CLOSE + m8-counterexample-shrinking-scoping).
- **268 unit tests + 35 sandbox tests** registrados como green al cierre de m8-06.
- **1 report de cierre** `docs/milestones/M8-CLOSE.md` (114 líneas) firmado `m8-06` con precedencia explícita sobre `m7-close-report.md` §7.

Esto cambia el alcance de M8.1 de "construir el foundation" a **"preservar + inventariar el foundation ya existente y declarar la obsolescencia del ROADMAP §M8"**. Reconstruir el capítulo sería duplicar trabajo verificablemente mergeado a `main` y traicionar la regla "no falsear una entrega" (ROADMAP §3 + ADR-0004).

Simultáneamente se descubre que mi `main` está **70 commits ahead of `origin/main @ 99d6e603`** con 0 commits ahead en la otra dirección. Esa divergencia significa que he estado avanzando (H1.x + M6 + M7) sobre una base distinta a la canónica remota. M8 también está en `origin/main`, pero no solo ahí — los tags están en mi local, lo que confirma que cuando se hizo el reconcile previo, los commits M8 ya eran ancestros comunes.

Este ADR es el primer slice que reconoce formalmente la situación y la congela en un artefacto auditable, en línea con la regla §0.4 de "corrección aditiva + cadena de correcciones".

## 3. Alternatives considered

### 3.1 Re-ejecutar M8 desde cero (rechazado)

Habría requerido: borrar 6 tags, revertir 6 merges, destruir 268 tests verdes + 35 sandbox tests verdes. Eso sería:
- (a) Violar la regla ROADMAP §3 "no falsear una entrega".
- (b) Perder 6,712 LoC de código mergeado y verificado.
- (c) Ignorar 14 milestones + 1 close report firmados.
- (d) Romper la regla §0.4 de "corrección aditiva + cadena de correcciones".
- (e) Generar conflictos con branches `feat/m8-0X-*` que aún podrían existir (CC#53 los limpió en m9-65/66 pero solo en origin/main; mi main puede tener refs dangling — a verificar antes de re-ejecutar).

**Rechazado** por todas las anteriores.

### 3.2 Solo declarar M8 CLOSED sin inventario detallado (rechazado)

Habría perdido el contexto de qué hace cada shrinker, qué tags lo marcan, qué tests lo cubren. El "preservar e inventariar" del ROADMAP §M8 §81 exige granularidad. Un release-note de una línea no es inventario.

**Rechazado**.

### 3.3 ADR-0026 con tabla detallada de cada artefacto + SHA + estado + refactor propuesto (aceptado)

Es el alcance mínimo para cumplir literalmente con "preservar e inventariar" sin reconstruir. Es docs-only, reversible, verificable.

**Aceptado** (esta decisión).

### 3.4 ADR-0026 + commit de ROADMAP refactor inmediato (rechazado por scope)

Mezclar inventario + refactor de ROADMAP en el mismo ADR aumenta el blast radius y dificulta rollback. M8.1 entrega el inventario + decisión; el refactor del ROADMAP puede ser M8.8 (slice dedicado). Mantener slices pequeños = mejor recoverability.

**Rechazado**.

### 3.5 No escribir ADR-0026 y proceder directamente con M9 (rechazado)

Saltar M8.1 dejaría el cierre M8 sin documentación canónica de preservación. Cualquier agente que reanude la sesión se encontraría con un ROADMAP §M8 "no hecho" mientras los tags + código están mergeados — necesitaría re-descubrir el estado real. ADR-0026 es la fuente de verdad post-descubrimiento.

**Rechazado**.

- ADR-0026 no es ejecutable; requiere acción manual posterior (rebase o push) para que el conocimiento fluya a origin/main.
- El ROADMAP §M8 obsoleto sigue visible hasta que se ejecute el refactor propuesto (M8.8 o similar).

- M8.1 no genera tests nuevos (M8 ya está validado por los 268 + 35 existentes).
- M8.1 no genera código nuevo (preservación, no construcción).
- M8.1 no requiere merge a `main` (docs-only en ADR directory, single commit).
