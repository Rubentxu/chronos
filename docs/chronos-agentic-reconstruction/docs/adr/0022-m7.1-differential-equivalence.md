**Status:** Accepted

**Cycle:** M7 / M7.1 (differential execution v2, criterion of semantic equivalence + hierarchical hashes)
**chronos HEAD:** `f9a3ae02` (post-M6.7 STATE/JOURNAL alignment).
**Spike location:** off-repo, durable path `/home/rubentxu/m7-spikes/m7.1-differential-equivalence/`.

## 1. Context

ROADMAP §M7 §77 lists M7.1 as "criterio de equivalencia semántica y
hashes jerárquicos". M6 closed (7/7) — `chronos_invocation_id`s are
distinct per service, `trace_id` correlates cross-service, the
pipeline survives load, recovery, and error paths. M7 begins with the
**differential** question: given two recorded sessions, did they
produce the same *behaviour*?

The naïve answer — "compare event streams byte-exact" — fails for
production traces:

- **Timestamp drift.** Same request re-run on a different host has
  microsecond-level clock differences. Naïve comparison flags
  equivalent runs as divergent.
- **Field order.** `Vec<(String, EventField)>` iteration order is
  not stable across `HashMap` insertions. Naïve comparison flags
  semantically identical events as divergent.
- **Event order within an invocation.** Concurrency + scheduler
  jitter reorder events. Naïve comparison flags equivalent
  invocations as divergent.
- **Invocation order within a session.** Independent invocations
  execute in non-deterministic order. Naïve comparison flags
  equivalent sessions as divergent.

M7.1 must answer: *given an equivalence criterion, when are two
sessions "the same"?*

## 2. Decision

**Accepted.** M7.1 introduces three primitives in a single library
crate `m7_1_differential_equivalence`:

1. **`EquivalenceSpec`** — a 2-flag struct declaring which sources of
   non-determinism are *deliberately ignored*. Default ignores
   timestamps and field order; strict ignores nothing.
2. **Canonical bytes** — a length-prefixed, type-tagged encoding of
   `ChronosEvent` + `EventField` under a spec. Two events that
   produce equal canonical bytes will produce equal hashes.
3. **Three hierarchical hashes** — `hash_event_canonical`,
   `hash_invocation_canonical`, `hash_session_canonical`. Each is
   **deterministic** (FNV-1a 64-bit with explicit constants), and
   each is **order-independent** over the level below (events within
   an invocation, invocations within a session).

```
event (probe + fields + ts?)  → canonical bytes  → FNV-1a 64-bit
                                              ↑
                                         sort by hash
                                              ↓
invocation (events)            → sorted hashes → FNV-1a 64-bit
                                              ↑
                                         sort by hash
                                              ↓
session (invocations)          → sorted hashes → FNV-1a 64-bit
```

### 2.2 The three primitives

```rust
pub struct EquivalenceSpec {
    pub ignore_timestamps: bool,
    pub ignore_field_order: bool,
}

pub fn equivalence_spec_default() -> EquivalenceSpec
pub fn equivalence_spec_strict() -> EquivalenceSpec

pub fn canonical_field_bytes(field: &EventField) -> Vec<u8>
pub fn canonical_event_bytes(event: &ChronosEvent, spec: &EquivalenceSpec) -> Vec<u8>

pub fn hash_event_canonical(event: &ChronosEvent, spec: &EquivalenceSpec) -> u64
pub fn hash_invocation_canonical(events: &[ChronosEvent], spec: &EquivalenceSpec) -> u64
pub fn hash_session_canonical(invocation_hashes: &[u64], spec: &EquivalenceSpec) -> u64

pub enum DiffVerdict { Equivalent, Differ }
pub fn diff_session_hashes(a: &[u64], b: &[u64], spec: &EquivalenceSpec) -> DiffVerdict
```

### 2.3 Why FNV-1a

`std::collections::hash_map::DefaultHasher` is **not stable** across
Rust versions — its seed is randomised per execution. For a hash that
must reproduce byte-exact across runs and Rust upgrades, we need a
well-known hash function. FNV-1a 64-bit is:

- **Deterministic** — explicit `FNV_OFFSET = 0xcbf29ce484222325` and
  `FNV_PRIME = 0x100000001b3` constants; no random seed.
- **Pure stdlib** — 10 lines, no `ring`/`sha2`/`blake3` external dep.
- **Fast** — non-cryptographic, ~2× the throughput of SipHash on
  short inputs.
- **64-bit output** — collision probability is negligible for the
  session sizes M7.1 targets (typical session: <1000 invocations).

The trade-off: FNV-1a is not cryptographic. An attacker who can
choose inputs could engineer collisions. M7.1 is for **internal
regression detection**, not authentication, so collision-resistance
against adversarial input is not a requirement. M7.4 will measure
collision probability empirically on the UAT corpora.

### 2.4 Canonical bytes format

Each `EventField` is encoded as `<tag:u8> <len:u32 LE> <bytes>`:

| Field type | tag | payload |
|---|---|---|
| `Str(String)` | `0x01` | UTF-8 bytes |
| `Int(i64)` | `0x02` | 8 bytes LE |
| `Bool(bool)` | `0x03` | `0x00` or `0x01` |
| `DomainRef(String)` | `0x04` | UTF-8 bytes |

Length-prefixing disambiguates boundaries. Tag-bytes prevent
type-confusion attacks (e.g. `Str("1")` and `Int(1)` hash differently
even though they look equal in display).

A `ChronosEvent` is encoded as `<probe_len:u32 LE> <probe_bytes>
[ts_micros:8 LE if not ignored] <n_fields:u32 LE>
<key_len:u32 LE> <key_bytes> <field>...` — fields are sorted by key
when `ignore_field_order` is true (BTreeMap canonicalisation).

### 2.5 Spec semantics

| Spec | ignores ts? | ignores field order? | Use case |
|---|---|---|---|
| `equivalence_spec_default()` | yes | yes | "Did the system behave the same?" (production regression) |
| `equivalence_spec_strict()` | no | no | "Did the system produce the *exact same bytes*?" (recorded incident replay) |

Future flags (M7+): `ignore_probe_set`, `ignore_branch_profile`,
`ignore_value_variance`, `ignore_field_subset(Vec<String>)`. M7.1
stops at 2 flags because the spike is the foundation; more flags
will be added when BehaviourFingerprint (M7.3) needs them.

## 3. Alternatives considered

- **`sha2` / `blake3` external dep.** Rejected: M6.{1..7} are
  pure-stdlib; bringing in a hash crate would be the first external
  hash dependency. FNV-1a is sufficient.
- **`DefaultHasher` with `with_seeds(...)`.** Rejected: the seed
  parameter affects only the *initial state*; the `Hasher` trait
  method dispatch (write, finish) is still subject to compiler
  optimisation differences. FNV-1a is byte-exact across versions.
- **No canonical bytes (hash fields directly).** Rejected: the spec
  is "ignore X"; we need a *transformation* of the event under the
  spec, not just a hash. Canonical bytes make the transformation
  inspectable and reusable.
- **Order-sensitive invocation hash.** Rejected: would force the
  caller to canonicalise event order before hashing. The
  order-independent hash *is* the canonicalisation.
- **Persistent invocation-hash history (e.g. BTreeMap).** Rejected:
  adds I/O. The in-memory `Vec<u64>` is sufficient; persistence is
  M7.2's job.
- **`PartialEq` derive on `ChronosEvent`.** Rejected: would couple
  the equivalence criterion to the type. `EquivalenceSpec` is
  external — callers choose what counts as "the same".

## 4. Consequences

### Positive

- **Stable across runs.** FNV-1a + explicit constants = no surprise
  hash drift across Rust versions. A hash recorded today matches a
  hash computed on `rustc 1.99` tomorrow.
- **Composable.** M7.2 (alignment by invocation/context) and M7.3
  (BehaviourFingerprint) consume the three primitives. They do not
  need to re-implement canonicalisation.
- **Honest about what it ignores.** The spec is a *first-class*
  value, not a flag in a config file. Callers see what is being
  ignored.
- **No silent lies.** `Differ` is honest. Two events that differ in
  any non-ignored field produce different hashes; two events that
  differ only in ignored fields produce equal hashes.
- **Auditable.** `canonical_event_bytes` exposes the bytes that
  feed the hash. If a hash surprises the user, they can dump the
  bytes and diff manually.

### Negative / costs

- **No probabilistic semantics.** FNV-1a is 64-bit; collision
  probability is `~1/2^32` per session pair (birthday paradox).
  Acceptable for typical session sizes (< 10k invocations), but a
  billion-session corpus would see ~1 collision. M7.4 will measure.
- **Field-order canonicalisation requires `BTreeMap`.** Per-event
  overhead: O(n log n) where n = number of fields. For typical
  n ≤ 16, this is negligible (~50 ns).
- **Spec flags are limited.** Only `ignore_timestamps` and
  `ignore_field_order`. Future M7 sub-cycles will add more flags
  (probe-set, branch-profile, value-variance). Adding a flag is a
  breaking change to the canonical bytes format (callers with
  recorded hashes must invalidate).
- **Hash output is opaque.** Two equal hashes *might* collide (with
  probability ~1/2^64 per pair). The smoke test uses 3 sessions ×
  3 specs = 9 hashes; collision is not detectable in this sample.
  M7.4 will run a fuzz-style collision hunt.

### Neutral

- **`u64` output.** 64 bits is what FNV-1a produces; not 128-bit
  (xxhash3 would be, but we don't pull xxhash). For M7.1's scope,
  64 bits are enough.
- **`DiffVerdict` enum is binary.** `Equivalent | Differ`. No
  "warning" or "uncertain" state. Callers who need a confidence
  score should use a different hash (or count collisions on
  retries).

## 7. M7 chapter plan

M7.1 is the foundation. M7.2..M7.4 build on it:

- **M7.2** — alignment by `chronos_invocation_id` / `trace_id`,
  not by timestamp. The hash primitives are order-independent
  *within* a level; M7.2 must align events **across** two sessions
  that may have different invocation counts.
- **M7.3** — `BehaviourFingerprint` as a *summary* of an
  invocation family: branch profile, callees, exception profile,
  mutated state fields, return-shape class. M7.1 hashes supply the
  building blocks; M7.3 chooses what to include.
- **M7.4** — UAT-M7-01/02 against recorded corpora; cost/memory
  baselines for the hash primitives; collision hunt on a
  billion-event fuzz corpus.

## 8. Out-of-scope (explicit non-goals)

- **Persistent storage of canonical bytes.** M7.2 stores hashes; M7.1
  does not.
- **Hash for `RecordedInvocation` itself.** M7.1 operates on
  `ChronosEvent` only. M7.2 will align on `RecordedInvocation`
  metadata.
- **Cryptographic hash.** FNV-1a is non-cryptographic. Adversarial
  collision is not a concern (M7.1 is internal regression
  detection, not auth).
- **128-bit hash.** xxhash3 / BLAKE3 would give 128-bit output but
  add an external dep. M7.4 will re-evaluate if collisions appear.
- **Per-probe canonicalisation.** Two events with the same probe but
  different semantic meaning (e.g. `checkout` vs `checkout.refund`)
  hash differently only because of the probe name. M7.1 does not
  parse probe names; M7.3 may.
- **Streaming hash.** M7.1 hashes the entire session at once. M7.2
  may add incremental alignment, but M7.1 stays batch.
