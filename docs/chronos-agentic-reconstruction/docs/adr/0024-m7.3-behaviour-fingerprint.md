# ADR-0024 — M7.3 BehaviourFingerprint (session-level summary)

**Status:** Accepted
**Date:** 2026-09-22
**Cycle:** M7 / M7.3 (differential execution v2, fingerprint)
**chronos HEAD:** `777d9dfb` (post-M7.2 STATE/JOURNAL alignment).
**Spike location:** off-repo, durable path `/home/rubentxu/m7-spikes/m7.3-behaviour-fingerprint/`.

## 1. Context

ROADMAP §M7 §77 lists M7.3 as "fingerprint de comportamiento de
sesión que consume `AlignmentReport`". M7.1 closed
(`hash_*_canonical` over FNV-1a 64-bit, deterministic across Rust
versions, spec-tunable via `EquivalenceSpec`). M7.2 closed
(alignment by `chronos_invocation_id` primary + `trace_id` fallback,
4-way classification: matched / mismatched / only_in_a / only_in_b,
rejection of ambiguous sessions per ADR-0004).

The open question after M7.2 is: **given an `AlignmentReport`, what
do we write to a regression log that lets a future run answer "is this
session equivalent to a known-good baseline?".** The naïve answer —
serialize the report's `Vec`s — gives O(n) bytes per comparison and
forces byte-exact array equality. The deep answer is a compact,
deterministic fingerprint that

1. makes ordering irrelevant (insertions might arrive in any order),
2. tracks content (same shapes with different specific hashes stay
   distinguishable — otherwise two runs that drift in payload but
   agree on counts would alias),
3. remains reversible by category (matched / mismatched / only-in),
   so a regression report shows where the divergence is.

M7.3 closes that gap.

## 2. Decision

Adopt a single `BehaviourFingerprint` type with two FNV-1a 64-bit
hashes derived deterministically from M7.2's `AlignmentReport`. The
hashing consumes M7.2's per-pair `hash_a` / `hash_b` (which are
themselves M7.1 FNV-1a 64-bit canonical hashes computed once per
`align_sessions` call) — M7.3 does **not** recompute hashes. Pure
function over the report. No I/O, no time, no RNG.

### 2.1 — `BehaviourFingerprint` shape

```rust
pub struct BehaviourFingerprint {
    pub aggregate_hash: u64,
    pub fingerprint_hash: u64,
    pub matched_count: usize,
    pub mismatched_count: usize,
    pub only_in_a_count: usize,
    pub only_in_b_count: usize,
}
```

Two hashes, four counts. Each has a distinct purpose:

- `aggregate_hash` covers the *content* of every classified invocation
  via a (status_tag, hash_a, hash_b, delta) byte stream sorted by
  `(status, primary_hash)` for insertion-order independence. Two sessions
  with identical (matched/mismatched/only-in) hashes match exactly; if
  any specific invocation differs, the aggregate hash differs.
- `fingerprint_hash` covers the *shape* via a (status_tag, primary_hash,
  delta) byte stream sorted identically. Same shape, same fingerprint;
  same content, same aggregate.

The two together let callers assert either of two equivalence styles
strictly:

```rust
pub fn fingerprint_equiv(a, b) -> bool {
    a.fingerprint_hash == b.fingerprint_hash && a.aggregate_hash == b.aggregate_hash
}

pub fn fingerprint_shape_only_equiv(a, b) -> bool {
    a.fingerprint_hash == b.fingerprint_hash
}
```

The shape-only variant exists because two runs that "did the same
amount of work" but with different specific values are common in
chaos/replay tests — and worth distinguishing from "identical
behaviour".

### 2.2 — Stream layout (per `InvocationAlignment`)

For the **aggregate** stream, per pair emit:

```
[status_tag: u8][hash_a: u64][hash_b: u64][delta_or_sentinel: u64]
```

For the **fingerprint (shape)** stream, per pair emit:

```
[status_tag: u8][primary_hash: u64][delta_or_sentinel: u64]
```

`status_tag` is a single byte per status (`0x01` Matched, `0x02`
Mismatched, `0x03` OnlyInA, `0x04` OnlyInB), deliberately small so the
status discriminator is independent of any payload.

`primary_hash` is `min(hash_a, hash_b)` when both are `Some(...)`,
the present side when exactly one is `Some`, or `0` when neither is
present (won't happen in a well-formed M7.2 report but defined for
robustness).

`delta_or_sentinel` is `delta_event_count: i64 → u64` bits when
present, otherwise `0x8000_0000_0000_0000` (`i64::MIN`) as a
distinguished sentinel out of the plausible small-real-delta range.

### 2.3 — Sorting key

For determinism, each pair is keyed by `(status_tag, primary_hash)`
and sorted ascending before streaming into the FNV-1a fold. The
sorted-stream-then-hash construction guarantees two alignment reports
with the same `(status, primary, delta)` multiset produce the same
hash regardless of which side of `align_sessions` enumerated the pair
first.

### 2.4 — Why FNV-1a (matching M7.1)

- Deterministic across Rust versions (no SipHash random seed).
- Pure stdlib, no external crate.
- ~10-line implementation.
- 64-bit sufficient for typical session sizes (collision probability
  ~5×10⁻⁸ for two pairs of 1000 hashes — see §5 collision analysis).
- Not cryptographic — M7 is internal regression detection, no auth.

### 2.5 — Public surface

```rust
pub fn session_fingerprint(report: &AlignmentReport)
    -> Result<BehaviourFingerprint, FingerprintError>;

pub fn fingerprint_equiv(a: &BehaviourFingerprint, b: &BehaviourFingerprint) -> bool;

pub fn fingerprint_shape_only_equiv(a: &BehaviourFingerprint, b: &BehaviourFingerprint) -> bool;

pub fn summary(f: &BehaviourFingerprint) -> FingerprintSummary;
```

`FingerprintError` is `EmptyReport` — `session_fingerprint` rejects
empty reports so a "no work happened" scenario doesn't alias with
"actually all-work-was-equivalent".

`FingerprintSummary` is a human-readable structure with three strings:
`aggregate_hash_hex: 16-hex`, `fingerprint_hash_hex: 16-hex`, and
`counts_line: "matched=N mismatched=N only_in_a=N only_in_b=N"`. Used
by the smoke example and the CLI probe.

## 3. Alternatives considered

### 3.1 — Store the `AlignmentReport` verbatim

Rejected: O(n) bytes per comparison; byte-exact equality forces
ordering-dependence and breaks when the report struct gains new
fields. A fingerprint summarises the equivalence-class without
preserving the per-pair detail (which is what log files are for).

### 3.2 — Single hash (aggregate == fingerprint)

Rejected: confuses "same shape" with "same content". Two runs with the
same matched count but different specific invocations would alias,
defeating regression detection where specific payload drift matters.

### 3.3 — Per-status hash

Rejected: more noise in the contract. We need exactly two predicates
("is this identical?" / "is this the same shape?"). Per-status
breakdown does not buy signal above the primary key + counts.

### 3.4 — Cryptographic hash (SHA-256)

Rejected: heavier dependency for no actual benefit. M7 is internal
regression detection, no auth. Cross-version determinism is the
hard constraint; FNV-1a nails it.

### 3.5 — Persistent storage of canonical bytes

Explicitly out of scope (deferred to M7.4+). BehaviourFingerprint is
an in-memory summary.

## 4. Consequences

### 4.1 — Positive

- **Determinism.** Two alignment reports with the same `(status,
  primary, delta)` multiset hash identically regardless of pairwise
  enumeration order.
- **Two predicates, six lines.** `fingerprint_equiv` and
  `fingerprint_shape_only_equiv` cover both common regression
  patterns.
- **Counts preserved.** `BehaviourFingerprint` carries matched /
  mismatched / only_in_a / only_in_b directly, no need to re-walk
  the report.
- **Tests are fast.** 20 contract tests + smoke run in <0.01s.
- **Dependencies closed-loop.** M7.3 consumes M7.2's
  `hash_a` / `hash_b` (which are M7.1 FNV-1a); no recomputation.

### 4.2 — Negative / Trade-offs

- **No field-level diff.** A "matched but with a changed field"
  report shows up only as an aggregate_hash mismatch. Resolution is
  M7.4 scope (UAT-M7-01/02 evidence chain).
- **Status symmetry.** `OnlyInA` and `OnlyInB` produce different
  status tags in the byte stream. Swapping A and B is therefore a
  *not-equal* equivalence assertion. Documented in Test 14 (only-in
  fingerprint invariant under inversion).
- **Spec dependence at M7.2 boundary.** M7.2's `hash_a` / `hash_b`
  were computed by `align_sessions` with whatever `EquivalenceSpec`
  was passed. Two alignments using different specs of the same
  inputs *may* differ — and that is correct: the fingerprint is
  tracking the spec's view. Documented in Test 15 (idempotency under
  repeated alignment).

### 4.3 — Collision analysis (FNV-1a 64-bit, ~5×10⁻⁸)

For a typical session of 1000 invocations, the probability of an
unintended collision across two unrelated sessions is roughly
5×10⁻⁸ — comparable to bug-class flakiness, well below the M7.4
collision-hunt threshold. Collision hunt itself is M7.4 scope.

### 5.4 — Test categories covered (20 tests)

- **Empty / single-invocation equivalence (Tests 1–3, 9):** EmptyReport
  error path, single-invocation equiv, two-invocation equiv under
  order swap.
- **Mismatch / only-in invariants (Tests 4, 5, 14):** Aggregate hash
  changes on content divergence; only_in_a / only_in_b counts survive;
  A↔B inversion visibly toggles status tag.
- **Spec sensitivity (Tests 6, 15):** Strict spec rejects timestamp
  drift via Mismatched status; same spec twice gives identical
  fingerprint.
- **Determinism under ordering (Tests 7, 17, 19):** Order-independent
  across insert/swap/reverse; session reordering yields `equiv`; same
  report identical fingerprint (idempotency).
- **Shape vs content (Test 8):** Shape-only equiv disagrees on
  content-only changes.
- **Scale (Tests 11, 18):** 50-invocation stable in microseconds;
  fingerprint total matches alignment total.
- **Summary rendering (Tests 9, 20):** 16-hex hashes, count line
  format, uniqueness of summary across scenarios.
- **Trace fallback path (Test 10):** `align_sessions` fallback to
  `trace_id` produces valid `fingerprint`.
- **Mixed-status (Test 12):** `matched + mismatched + only_in_a +
  only_in_b` all counted.

## 8. Out-of-scope (M7.4+)

- Persistent storage of canonical bytes (M7.4+ evidence chain).
- Cryptographic hash (M7.3 inherits FNV-1a; no auth).
- 128-bit hash (FNV-1a 64-bit is sufficient per §4.3 collision
  analysis).
- Per-probe canonicalisation (M7 operates at session level).
- Streaming hash (cap by session size, not memory-bounded).
- Field-level diff (covered by per-pair logs in M7.4 evidence).
- Cross-session fingerprint aggregation (per-session fingerprint is
  the unit of regression detection; aggregator is M7.4).
- Alignment across heterogeneous event sources (M4R.3 overlay
  separated into a different concern).
- Memory-pressure-aware streaming (M7.4 cost baseline).
