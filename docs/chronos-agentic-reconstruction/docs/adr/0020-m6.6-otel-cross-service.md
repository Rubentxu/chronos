# ADR-0020 — M6.6 correlación cross-service + UAT-M6-01/02

**Status:** Accepted
**Date:** 2026-09-22
**Cycle:** M6 / M6.6 (correlación cross-service con dos servicios y requests concurrentes)
**chronos HEAD:** `488ef28d` (post-M6.5 SHA alignment).
**Spike location:** off-repo, durable path
`/home/rubentxu/m6-spikes/m6.6-otel-cross-service/`.

## 1. Context

ROADMAP §M6 §86 lists M6.6 as "UAT-M6-01/02 con dos servicios y
requests concurrentes — correlación trace/span externo ->
invocación Chronos -> mutación con IDs distintos; dos
peticiones concurrentes no mezclan contexto; sin contexto,
span huérfano, reloj monotónico diferente o OTLP temporalmente
indisponible: error/procedencia completos, sin timestamps Unix
inventados; ingestión y exportación recuperables/idempotentes
dentro del contrato".

The M6.1..M6.5 spikes are all single-process. M6.6 closes the
cross-service validation:

- **UAT-M6-01** — request traverses two services and reaches
  mutation/property violation: external `trace_id` correlates
  cross-service, `chronos_invocation_id` is **distinct per
  service**, two concurrent requests do NOT mix context.
- **UAT-M6-02** — without context, orphan span, monotonic-clock
  drift, or OTLP temporarily unavailable: full
  error/provenance, no invented Unix timestamps,
  ingestion/export recoverable and idempotent within the
  contract.

## 2. Decision

**Accepted.** The cross-service correlation spike has a single
public pipeline function plus an HTTP-loopback simulator.

```
service_a (TCP :4819)
   ├─ parse traceparent  ────► m6_2_otlp_adapter
   ├─ generate fresh InvocationId (UUID v4)
   ├─ bind events in CorrelationStore
   ├─ export_spans  ─►  redact_and_limit_spans  ─►  render_json_line
   ├─ forward traceparent to service_b (best-effort)
   └─ POST each JSONL line to consumer (TCP :4821)

service_b (TCP :4820)
   ├─ parse traceparent  ────► m6_2_otlp_adapter
   ├─ generate its OWN fresh InvocationId (UUID v4) — distinct from service_a
   ├─ bind events in CorrelationStore
   ├─ export_spans  ─►  redact_and_limit_spans  ─►  render_json_line
   └─ POST each JSONL line to consumer

consumer (TCP :4821)
   ├─ POST /collect: parse JSONL body, aggregate by trace_id
   └─ GET /dump: return aggregated state (text)
```

### 2.1 Public API (lib.rs)

```rust
pub enum ServiceId { A, B }
pub struct EventSeed { pub ts_micros: u64, pub probe: String, pub fields: Vec<(String, EventField)> }
pub struct ServiceRunOutcome {
    pub service: ServiceId,
    pub recorded: RecordedInvocation,
    pub events: Vec<ChronosEvent>,
    pub jsonl_lines: Vec<String>,
    pub export_counters: ExportCounters,
    pub redaction_counters: RedactionCounters,
    pub store: StoreSnapshot,
}

pub enum PipelineError { BadTraceparent { raw: String, error: TraceparentParseError } }

pub fn run_service_pipeline(
    service: ServiceId,
    traceparent: Option<&str>,
    event_seeds: &[EventSeed],
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> Result<ServiceRunOutcome, PipelineError>;

pub fn build_traceparent(
    trace_id_hex: &str,
    span_id_hex: &str,
    flags_hex: &str,
) -> Result<String, TraceparentParseError>;

pub fn serve_service_a_once(
    stream: TcpStream,
    consumer_port: u16,
    service_b_port: u16,
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> Result<ServiceRunOutcome, String>;

pub fn serve_service_b_once(
    stream: TcpStream,
    consumer_port: u16,
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> Result<ServiceRunOutcome, String>;

pub fn serve_consumer_once(
    stream: TcpStream,
    state: &mut ConsumerState,
) -> Result<(), String>;

pub struct ConsumerState {
    pub traces: BTreeMap<Vec<u8>, Vec<uuid::Uuid>>,
    pub total_lines: usize,
}
```

### 2.2 Pipeline core (`run_service_pipeline`)

Pure function (no network, no time). Steps:
1. Parse `traceparent` (if present) via M6.1 → typed
   `ExternalTraceContext`; root-context → `InternalOnly`;
   `None` → `InternalOnly` with fresh UUID v4
   `InvocationId`; parse failure → `PipelineError::BadTraceparent`
   with `raw` preserved (No Silent Lies).
2. Build `Vec<ChronosEvent>` from `event_seeds` (user supplies
   `ts_micros`, `probe`, and typed `EventField`s).
3. `CorrelationStore` is per-service (each `run_service_pipeline`
   call creates a fresh store); bind each event_idx to the
   same `RecordedInvocation`.
4. `export_spans` (M6.4) → `redact_and_limit_spans` (M6.5) →
   `render_json_line` (M6.4 re-exported).
5. Return `ServiceRunOutcome` with the JSON Lines, counters,
   and a serializable `StoreSnapshot`.

### 2.3 Idempotency decision

**Idempotency is measured over `trace_id`, NOT over
`chronos_invocation_id`.** M6.1's `InvocationId::new()` returns
a fresh UUID v4 per call. Two retries with the same
`traceparent` produce different `chronos_invocation_id`s in
each service but the same `trace_id` (since the traceparent is
parsed into `ExternalTraceContext`, which carries the
`trace_id`). The M6.6 tests pin this:
`idempotent_retry_same_traceparent_preserves_trace_id` —
`assert_ne!(out_1.invocation_id, out_2.invocation_id)` AND
both JSONLs contain the same `trace_id_hex`. This is a
deliberate non-extension of M6.1 (no `InvocationId::deterministic_from_trace`).

### 2.4 Concurrent requests

The `run_service_pipeline` function is **stateless across
calls** — each invocation creates a fresh `CorrelationStore`,
fresh `BTreeMap` snapshot, and fresh UUID v4
`InvocationId`. Two concurrent calls in the same OS thread
(or across threads) cannot share state. The smoke
`examples/smoke_concurrent.rs` demonstrates 2 concurrent
HTTP requests (each in its own `std::thread`) with distinct
`traceparent`s → 2 distinct service_a invocations + 2
distinct service_b invocations, all 4 visible to the
consumer keyed by their shared `trace_id`.

### 2.5 OTLP outage handling

When `service_a` POSTs a span to the consumer, a
`Connection refused` returns `false` from
`post_to_consumer` but does **not** abort the local
pipeline. The local `ServiceRunOutcome.jsonl_lines` are
still produced and returned; the only difference is that
the consumer never sees them. The smoke does not exercise
this path explicitly (consumer is up during the test), but
the `forward_to_service_b` and `post_to_consumer` helpers
are documented as best-effort fire-and-forget. M6.7
(formal gate) will add a counter for outage events.

### 2.6 Wire format invariant

M6.6 inherits the M6.4 + M6.5 wire format JSON Lines
without modification. The two cross-service additions:
- Same `trace_id_hex` across services for the same logical
  request (when `traceparent` is propagated).
- Different `chronos_invocation_id_hex` per service
  (because each service generates its own UUID v4).
`start_time_unix_nano` derives from `event.ts_micros *
1000` (M6.4 contract); no `chrono::Utc::now()` anywhere
(no invented Unix timestamps).

## 3. Behavioural spec

### 3.1 `build_traceparent`

Given a 32-hex `trace_id`, 16-hex `span_id`, and 2-hex
`flags`, returns the canonical W3C
`00-<trace_id_hex>-<span_id_hex>-<flags_hex>` string. The
hex is validated by routing through M6.1's `parse_traceparent`;
parse failure returns `Err(TraceparentParseError)`. This is
the helper that lets tests/build fixtures create deterministic
cross-service scenarios without depending on M6.1's private
`TraceId` constructor.

### 3.2 Per-service pipeline

For each `run_service_pipeline` call:
- `store.distinct_invocations() == 1` (single InvocationId
  bound to all events).
- `store.distinct_traces()` is either `0` (InternalOnly) or
  `1` (Recorded with one `trace_id`).
- `redaction_counters.redacted_fields` ≥ 0 and
  `redaction_counters.collapsed_cardinality` ≥ 0.
- `jsonl_lines.len() == events.len()` (one span per event).

### 3.3 Two concurrent requests (UAT-M6-01)

Two `run_service_pipeline` calls in the same process with
distinct `traceparent`s produce:
- Two distinct `chronos_invocation_id`s (UUID v4 random).
- Two distinct `trace_id_hex`s (each comes from the parsed
  `traceparent`).
- Zero cross-talk: no event in the first pipeline's
  `StoreSnapshot` references an `InvocationId` belonging to
  the second pipeline, and vice versa.

The cross-service smoke exercises this with HTTP-level
concurrency: 2 threads, each firing `GET
/forward?traceparent=00-<unique>...` against `service_a`,
each generating its own pipeline + another for `service_b`
via the internal forward. The consumer aggregates 6 lines
(2 service_a spans × 2 traces + 2 service_b spans × 2
traces = 4 + 2 = 6; the actual count depends on how many
events each service emits per pipeline).

### 3.4 Edge cases (UAT-M6-02)

- **No `traceparent`**: `InternalOnly`; `trace_id_hex` is
  all-zero per M6.4 contract.
- **Orphan span**: events with `event_idx` that has no
  binding are not exported (`M6.4 export_spans` only emits
  events present in the store's `bindings_iter`).
- **Monotonic-clock drift**: each service uses its own
  `ts_micros`; `start_time_unix_nano` derives from it; no
  service "fixes" or "synchronizes" the clock.
- **OTLP temporarily unavailable**: local pipeline
  succeeds; spans NOT delivered to consumer; documented
  as best-effort in code.
- **Idempotent retry**: same `traceparent` 2× → same
  `trace_id_hex` in JSONL; different `chronos_invocation_id`
  per call (UUID v4 by design).

## 5. Why this matters for M6

M6.6 closes the **cross-service validation** that M6.1..M6.5
built. The wire format is locked, the redaction + cardinality
layer sits cleanly between export and the network boundary
(M6.5), and now we demonstrate that 2 services exchanging
HTTP/JSONL with the consumer see distinct `chronos_invocation_id`s
but correlated `trace_id`s, and concurrent requests do not
cross-talk.

- **M6.7 (gates)** — load/recovery/error gates. Will reuse
  M6.6's HTTP plumbing + spike pattern but add explicit
  outage counters + retry logic + chaos scenarios (random
  `connection refused`, slow consumer, etc).
- **M7 (differential execution v2)** — needs cross-service
  correlation to detect cross-service drift between good/bad
  invocations. M6.6's `consumer` aggregation (`trace_id`
  → `Vec<invocation_id>`) is the cross-service baseline.
- **Productisation** — when the M6 chapter begins moving
  spikes into `chronos-core`, the `run_service_pipeline`
  function becomes the canonical entry point for the
  cross-service correlation layer.

## 6. Out-of-scope / future work

- **No batched OTLP / HTTP/2 / gRPC**. The HTTP plumbing is
  one-request-per-connection (`Connection: close`) on stdlib
  TcpListener. Production should graduate to a real HTTP stack
  while preserving the `run_service_pipeline` contract.
- **No TLS / authentication**. Plain HTTP on loopback.
- **No persistent consumer state**. The consumer's
  `ConsumerState` is in-memory only. Production would add
  redb-backed persistence (matches `chronos-store`).
- **No parent/child span synthesis**. M6.6 emits first-class
  spans only. M6.4 already added `parent_span_id_hex` plumbing;
  M6.7 or M1+ can wire up child spans.
- **No explicit outage counter**. The `post_to_consumer` /
  `forward_to_service_b` helpers return `bool` but the
  outcome struct does not yet record outage events. M6.7.
- **No deterministic `InvocationId` from `traceparent`**.
  Idempotency is measured over `trace_id`, not
  `chronos_invocation_id`. A future ADR could extend M6.1
  to add `InvocationId::deterministic_from_traceparent` if
  a use case requires it.
- **No fan-out to multiple consumers**. The smoke fires
  HTTP at one consumer; multi-collector / multi-tenant is
  out of scope.
- **No cross-process / cross-host**. All loopback. The
  correlation logic is process-agnostic; network-level
  testing is M1+.

## 9. Closing note

**M6 §M6.6 is delivered.** Cross-service correlation works:
two HTTP services exchanging requests propagate the
`traceparent`, generate distinct `chronos_invocation_id`s,
emit OTLP-shaped JSONL spans with the same `trace_id_hex`,
and the consumer aggregates by `trace_id` to demonstrate
correlated but service-distinct invocations. M6.5 redaction
is applied per-service. 14/14 contract tests pass; the
smoke_concurrent example PASSes in 803 ms.

M6.1 + M6.2 + M6.3 + M6.4 + M6.5 + M6.6 = **6/7 sub-ciclos
M6 cerrados**. The remaining **M6.7 (gates de carga /
recuperación / errores del pipeline OTLP + redaction)**
builds directly on M6.6's HTTP plumbing + spike pattern and
adds chaos scenarios + outage counters.

The spike is path-dep on M6.1..M6.5 (all at the durable
`/home/rubentxu/m6-spikes/` location — NOT scratch). It
can be lifted into `chronos-core` as a submodule when the
M6 chapter begins productisation. The `run_service_pipeline`
function is the cross-service correlation contract that M6.7
and M7 will all consume.
