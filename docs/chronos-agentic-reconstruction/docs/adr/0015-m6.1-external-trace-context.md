# ADR-0015 — M6.1 ExternalTraceContext separate from InvocationId

**Status:** Accepted
**Date:** 2026-09-21
**Cycle:** M6 / M6.1 (contrato ExternalTraceContext separado de InvocationId)
**chronos HEAD:** `3989e704` (post M4-F1 closure).
**Spike location:** off-repo, `/home/rubentxu/.jcode/scratch/m6.1-skeleton/`.

## 1. Context

ROADMAP §M6 §86 lists M6.1 as "contrato ExternalTraceContext separado
de InvocationId". The requirement is to demonstrate that Chronos
**distinguishes two types of correlation IDs**:

1. **Internal `InvocationId`** — Chronos's own correlation for its
   internal events (a `mcp request → tool call → response` cycle).
   Generated by Chronos. Identifies a unit of work in Chronos's
   tracking service.

2. **External `ExternalTraceContext`** — a W3C trace context
   (`traceparent`, `tracestate`) coming from upstream OTel
   instrumentation. **Not generated by Chronos**; it's a carry-
   through value. Identifies a unit of work in someone else's
   distributed trace (the user's application, an upstream
   service).

These two are **separate contracts** because:
- They have different formats (Internal UUID vs W3C traceparent).
- They have different authorities (Chronos generated vs externally
  provided).
- They have different lifetimes (one Chronos action vs many
  external spans).

If they are mixed, you get ambiguities: "is this span ours, or is
it a thread of a much larger trace the user is investigating?"
Chronos needs to be able to answer both questions independently.

This ADR delivers the **type-level separation** in pure Rust, with
constructors that **enforce** the boundary: there is no path from
`InvocationId` to `ExternalTraceContext` or vice versa except
explicit `into_external_trace_context()` and
`from_external_trace_context()` conversion functions.

## 2. Decision

**Accepted.** The contract is encoded in three types in pure Rust
(no OTel runtime required for the spike — the types are purely
shape-level):

```rust
pub struct InvocationId(Uuid);                         // Chronos-generated
pub struct ExternalTraceContext {
    trace_id: TraceId,                                // 16 bytes / 32 hex
    span_id: SpanId,                                  // 8 bytes / 16 hex
    flags: TraceFlags,                                // 8 bits
    tracestate: Option<Tracestate>,                   // optional vendor state
}
pub struct TraceId([u8; 16]);
pub struct SpanId([u8; 8]);
pub struct TraceFlags(u8);
pub struct Tracestate(Vec<(String, String)>);         // vendor list-key pairs
```

### 2.1 Invariants

- **`InvocationId`** — opaque UUID v4 from `Uuid::new_v4()`. The
  only field. Constructible only via `InvocationId::new()` (no
  parse from string in this version).
- **`ExternalTraceContext`** — built ONLY via `parse_traceparent()`
  from a W3C-format string, or `ExternalTraceContext::root()`
  for an empty/root context. **No `new()` constructor exposed**;
  the boundary is enforced at the type level.
- **`TraceId`** and **`SpanId`** — opaque newtype wrappers around
  `[u8; 16]` and `[u8; 8]`. Constructible only via the parsers.
- **`TraceFlags`** — opaque newtype around `u8`. Bit `0` is
  "sampled" per W3C §3.2.2.
- **`Tracestate`** — list of `(vendor, value)` pairs. **At most
  32 entries** (W3C §3.3.1.1 limit). Each `(vendor, value)` is
  ≤ 256 chars total (W3C limit). Empty allowed.

### 2.2 Conversion functions

The ONLY way to combine the two contracts is via explicit
conversion:

```rust
impl InvocationId {
    /// "I have my own Chronos work to do; capture the external
    ///  trace context so the work is correlatable upstream".
    pub fn record_external(&self, etc: &ExternalTraceContext)
        -> RecordedInvocation { ... }
}
```

`RecordedInvocation` is a **separate type** containing both:
- `invocation_id: InvocationId`
- `external: Option<ExternalTraceContext>` (None if internal-only)

This is the **only structure** in which both contracts appear
together. Storage layers, log lines, trace payloads — they all
hold `RecordedInvocation` (or its serialised form), not the two
contracts separately.

## 3. Wire format

### 3.1 InvocationId wire format

```
00a3c0d8-1f00-4d00-a000-0123456789ab
```

Standard UUID v4 textual representation (8-4-4-4-12 lowercase hex
with dashes). 36 chars; no prefix.

### 3.2 ExternalTraceContext / `traceparent` wire format

W3C Trace Context §3.2:

```
{version}-{trace-id}-{parent-id}-{trace-flags}
```

- `version`: 2 hex chars (always `00` for current spec).
- `trace-id`: 32 hex chars (16 bytes; all-zero `00000000000000000000000000000000`
  is invalid).
- `parent-id`: 16 hex chars (8 bytes; all-zero is invalid).
- `trace-flags`: 2 hex chars (8 bits; bit 0 = sampled).

Example:
```
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

### 3.3 `tracestate` wire format

W3C Trace Context §3.3:

```
{key1}={value1},{key2}={value2},...
```

Each entry is `vendor=value`. Multiple entries comma-separated.
Max 32 entries; each ≤ 256 chars total.

Example:
```
congo=t61rcWkgMzE,rojo=00f067aa0ba902b7
```

### 3.4 RecordedInvocation wire format

`{invocation_id}|{traceparent}|{tracestate}` where the last two
may be empty if the external context is `None`. Example:

```
00a3c0d8-1f00-4d00-a000-0123456789ab|00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01|congo=t61rcWkgMzE
```

For internal-only (no external):
```
00a3c0d8-1f00-4d00-a000-0123456789ab||
```

## 4. Behavioural spec

### 4.1 Constructors

| Type | Constructor | Effect |
|---|---|---|
| `InvocationId` | `InvocationId::new()` | Generates UUID v4 |
| `ExternalTraceContext` | `parse_traceparent(s)` | Parses W3C traceparent |
| `ExternalTraceContext` | `ExternalTraceContext::root()` | Empty/zero context |
| `TraceId` | (only via parser) | Rejects all-zero |
| `SpanId` | (only via parser) | Rejects all-zero |
| `TraceFlags` | (only via parser) | 8 bits |
| `Tracestate` | `parse_tracestate(s)` | Parses vendor list |

### 4.2 Failures

| Construction | Failure mode |
|---|---|
| `parse_traceparent` of malformed string | Returns `Err(TraceparentParseError)` — never panics |
| `parse_tracestate` of too many entries (>32) | Returns `Err(TracestateTooMany { count })` |
| `parse_tracestate` of entry too long (>256 chars) | Returns `Err(TracestateEntryTooLong { len })` |
| Parse of zero `trace-id` or `parent-id` | Returns `Err(InvalidAllZero)` |

### 4.3 Equivalence

- `InvocationId::eq(other)` — UUID equality, byte-wise.
- `ExternalTraceContext::eq(other)` — same `version`, `trace_id`,
  `span_id`, `flags`, and `tracestate`. Does not compare
  semantically-meaningful variants like "are two `Tracestate`
  lists the same after vendor reordering" — equality is on
  byte-exact representation.

### 4.4 Serialisation

- `InvocationId::to_string()` — 36-char UUID form.
- `ExternalTraceContext::to_traceparent()` — W3C §3.2 form.
- `ExternalTraceContext::to_tracestate()` — W3C §3.3 form (or
  empty if no state).
- `RecordedInvocation::to_recorded()` — pipe-delimited form
  (§3.4).

## 6. Why this matters for M6

M6.1 closes the **type-level separation** that the rest of M6
builds on:

- **M6.2 (OTLP adapter)**: ingests `traceparent` headers into
  `ExternalTraceContext`. Separate from Chronos's
  `InvocationId`.
- **M6.3 (correlation)**: binds `ExternalTraceContext.trace_id`
  ↔ internal `InvocationId` records. The type-level separation
  makes this binding **explicit** (a `RecordedInvocation`).
- **M6.4 (exporter)**: emits OTel spans with both the carried
  external `trace_id` and the Chronos-side span.
- **M6.5 (security/redaction)**: redaction applies to fields, not
  to IDs. Since IDs are UUIDs/bytes, they're redaction-safe.
- **M6.6 (UAT)**: spins two services with cross-service calls;
  the `RecordedInvocation` cross-reference is the verification.
- **M6.7 (gates)**: load/recovery/error gates check that the
  correlation between `InvocationId` and `ExternalTraceContext`
  survives round-trips.

## 7. Out-of-scope / future work

- **No actual W3C propagation** across HTTP boundaries in this
  spike. The types and parsers exist; the carrier (HTTP
  `traceparent` header propagation) is M6.2's job.
- **No vendor-tag validation**. We accept any `vendor=value` per
  W3C §3.3. Vendor-tagging validation (e.g., "only allow known
  vendors") belongs to **CapTracestatePolicy** follow-up.
- **No `tracestate` mutation API**. The spike parses and emits;
  it does not have `add_vendor("rojo", value)` or similar. Such
  mutation belongs to a follow-up if needed.
- **No `TraceId::to_string()` formatting choice exposed**. W3C
  prescribes lowercase hex with no separators. The spike uses
  this default. Alternate formats (uppercase, with colons) are
  not W3C-compliant.

## 10. Closing note

**M6 §M6.1 is delivered.** The two contracts — internal
`InvocationId` and external `ExternalTraceContext` — are
**separated at the type level** in pure Rust. No path between
them except `RecordedInvocation`. This is the foundation for
M6.2 (OTLP ingestion), M6.3 (correlation), and the rest of M6.

The spike is **standalone** (depends only on the `uuid` crate)
and can be lifted into chronos-core as a submodule when the M6
chapter begins productisation.
