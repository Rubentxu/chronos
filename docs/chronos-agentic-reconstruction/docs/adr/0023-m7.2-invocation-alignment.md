# ADR-0023 — M7.2 alignment by invocation/context (not timestamps)

**Status:** Accepted
**Date:** 2026-09-22
**Cycle:** M7 / M7.2 (differential execution v2, alignment)
**chronos HEAD:** `1424f2f9` (post-M7.1 STATE/JOURNAL alignment).
**Spike location:** off-repo, durable path `/home/rubentxu/m7-spikes/m7.2-invocation-alignment/`.

## 1. Context

ROADMAP §M7 §77 lists M7.2 as "alineación por invocación/contexto, no
sólo timestamps". M7.1 closed — we have `EquivalenceSpec` and three
canonical FNV-1a hashes (`hash_event_canonical`,
`hash_invocation_canonical`, `hash_session_canonical`). M7.1 answers
*is the session equivalent?* but only for two sessions whose
invocations line up by **positional order**. M7.2 must answer the
question that comes before: *which invocation in A corresponds to
which invocation in B?*

The naïve answer — "line them up positionally" — fails for production
traces:

- **Independent invocations execute in non-deterministic order.**
  Two requests A and B both spawn the same 5 sub-invocations, but
  scheduler jitter reorders them.
- **Sessions merge across hosts.** Aggregated logs may interleave
  invocations from different sources.
- **Recovered sessions may carry extra or missing invocations.**
  An outage retry can produce 4 invocations on the recording side
  and 3 on the recovered side; we need to know which one is missing.

M7.1's `DiffVerdict::Equivalent | Differ` is a single-bit answer
applied to two entire sessions. M7.2 produces a per-invocation
alignment so the caller can:

1. Match by identity (`chronos_invocation_id` or `trace_id`), not
   position.
2. Detect **only-in-A** / **only-in-B** structural drift.
3. Detect **mismatched** invocations (same identity, different
   per-invocation hash under the spec).
4. Surface **delta_event_count** for matched pairs (events present
   on one side and missing on the other).

## 2. Decision

**Accepted.** M7.2 introduces a single library crate
`m7_2_invocation_alignment` with three building blocks:

1. **`InvocationWithEvents<'a>`** — pairs a `RecordedInvocation`
   (identity: `invocation_id` + `external: Option<ExternalTraceContext>`)
   with its events. This bridges the gap between M6.3's
   `RecordedInvocation` (no events) and M7.1's
   `hash_invocation_canonical(events: &[ChronosEvent], spec)` (which
   takes events directly).
2. **`Session<'a>`** — an ordered list of `InvocationWithEvents`.
   Order is recording order; alignment is order-**in**dependent (we
   sort by key).
3. **`align_sessions(a, b, spec) -> Result<AlignmentReport,
   AlignmentError>`** — the alignment algorithm:
   - Index A and B by `chronos_invocation_id` (BTreeMap).
   - Walk A; for each invocation, try to find a match in B:
     1. By `invocation_id` (primary key).
     2. Otherwise, by `trace_id` from the W3C `ExternalTraceContext`
        (fallback when one side lost the chronos envelope).
   - Anything in B not matched is `only_in_b`.
   - For matched pairs, hash both sides with
     `m7_1_differential_equivalence::hash_invocation_canonical` and
     decide `Matched` vs `Mismatched`.
   - Reject ambiguous sessions (two invocations sharing the same
     `chronos_invocation_id`) with `AlignmentError::AmbiguousInvocationId`.

The `AlignmentReport` carries four `Vec<InvocationAlignment>` slices
(`matched`, `mismatched`, `only_in_a`, `only_in_b`), plus a
`AlignmentKeyKind` per side (`Invocation` / `Trace` / `Mixed`) for
observability.

### 2.2 Why delegate to M7.1 for hashing

M7.1 already implements `hash_invocation_canonical(events, spec)` —
FNV-1a 64-bit, deterministic across Rust versions, sort+dedup of
event hashes per invocation. M7.2 does **not** re-implement hashing;
it only organises invocations by identity and reports the alignment
shape. This avoids hash drift between M7.1 and M7.2 and keeps the
spec/canonical-bytes contract in one place.

### 2.3 Why primary key = `chronos_invocation_id` (UUID v4)

`InvocationId::new()` returns a UUID v4 — collision probability is
astronomically low (~5.4×10⁻³⁷ per pair). The `M6.1` model treats
`InvocationId` as the canonical identity of a work-unit;
`ExternalTraceContext.trace_id` correlates *requests* across services,
but a single request can spawn multiple invocations (one per service
hop per M6.6 §2.3). The UUID v4 is stable per work-unit; the trace_id
is a request-level correlation key. Primary = UUID, fallback =
trace_id, in that order.

### 2.4 Why reject ambiguous sessions (vs. positional fallback)

If a session contains two invocations with the same `chronos_invocation_id`,
the alignment algorithm cannot pick a unique representative for that
key. M7.2 rejects with `AlignmentError::AmbiguousInvocationId {
invocation_id, occurrences }` instead of silently picking the first
occurrence. This is **No Silent Lies** (ADR-0004): the caller must
deduplicate before aligning, or treat the data as malformed.

### 2.5 Why `delta_event_count` only on matched/mismatched, not only-in-*

`delta_event_count` is `events_b.len() - events_a.len()`. For
`OnlyInA` / `OnlyInB`, one of the sides has no events (None).
Including delta on only-in would force a convention (e.g. always
positive on only-in-b) that obscures the *mismatch on a known pair*
semantic. M7.2 restricts delta to pairs and reports only-in counts
directly on the report.

## 3. Alternatives considered

### 3.1 Positional alignment (rejected)

Match A[i] ↔ B[i] for i = 0..min(|A|, |B|). Simple but wrong: scheduler
jitter reorders invocations in independent sessions, so even
"equivalent" sessions can have reordered invocation lists. Rejected.

### 3.2 Hash-only alignment (rejected)

Hash every invocation in A and B, match by equal hash. Fails when
two invocations share the same hash by coincidence (64-bit hash space,
birthday collision at ~4 billion invocations), and fails when the
sessions have only-in-* entries (no counterpart to hash against).
Rejected.

### 3.3 Always require trace_id (rejected)

Some chronos sessions are internal-only (no `external`), e.g. dry-runs
or pre-production replays. Forcing a trace_id would lock out those
use cases. UUID-only alignment with trace_id fallback covers both.

### 3.4 Streaming alignment (deferred to M7.4)

A streaming version that hashes and aligns on the fly (no full
materialisation of `Session`) is appealing for cost but requires
stable ordering guarantees that we cannot give for non-deterministic
recorders. Deferred to M7.4 (cost/memory baselines + UAT-M7-01/02).

## 4. Consequences

- **Producers benefit.** The M7.1 primitives stay single-source-of-truth;
  no duplicate canonicalisation or hashing code paths.
- **Callers gain observability.** A 4-way classification
  (matched/mismatched/only_in_a/only_in_b) plus per-pair hash + delta
  is enough to drive most UAT scenarios (UAT-M7-01, UAT-M7-02,
  UAT-M7-03 — see §6).
- **Memory cost.** Each `InvocationWithEvents` holds the events
  inline (`Vec<ChronosEvent>`). For a session with 10k events × 100B
  per event, that is ~1MB. Acceptable for M7.2 scope; M7.4 will
  measure cost/memory.
- **Time cost.** O(|A| + |B|) walk + O(|A| log |B|) BTreeMap lookups.
  Test 18 measures 1000 invocations on each side in < 1s on the dev
  box.
- **Out-of-scope (deferred).** Streaming alignment, cross-session
  alignment, alignment across heterogeneous event sources (M3 M4R.3
  overlay schema), alignment with field-level diff (vs hash-level
  diff). Each is a M7.4+ follow-up.

## 8. Out-of-scope (M7.3+)

- Persistent storage of canonical bytes or `AlignmentReport`.
- Hash for `RecordedInvocation` itself (we hash events per
  invocation; the identity UUID is the alignment key).
- Cryptographic hash (FNV-1a is non-cryptographic; M7.x is internal
  regression detection).
- 128-bit hash; per-probe canonicalisation; streaming hash.
- Field-level diff (vs hash-level diff) — would require storing the
  per-event canonical bytes for diff.
- Cross-session alignment (e.g. "did A and B diverge at the same
  invocation?").
- Alignment across heterogeneous event sources (M3 M4R.3 overlay
  schema).
- Memory-pressure-aware streaming alignment (M7.4 cost/memory
  baselines).
