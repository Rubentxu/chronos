# ADR-0019 — M6.5 seguridad/redacción y cardinalidad

**Status:** Accepted
**Date:** 2026-09-21
**Cycle:** M6 / M6.5 (seguridad/redacción y cardinalidad)
**chronos HEAD:** `c10bcc73` (post M6.4 merge).
**Spike location:** off-repo at **durable path** `/home/rubentxu/m6-spikes/m6.5-otel-redaction/`.

## 1. Context

ROADMAP §M6 §86 lists M6.5 as "seguridad/redacción y
cardinalidad". The requirement has two distinct pieces:

1. **Security / redaction** — secrets/PII in attribute
   values must be redacted before transmission. The
   canonical example: a `password` key with value `hunter2`
   must not be exported as-is; it must become a fixed
   placeholder `[REDACTED]`. This protects the system from
   leaking credentials through the telemetry stream.

2. **Cardinality limit** — distinct attribute keys per
   export call must be capped. The downstream OTel
   collector creates one series per unique key/value pair
   (Prometheus-style); unbounded cardinality can crash
   the collector with OOM. A cap with deterministic
   overflow handling prevents this.

This ADR delivers both, sitting between M6.4 (export
pipeline) and the network/stdout boundary.

## 2. Decision

**Accepted.** M6.5 is a **stateless redaction + cardinality
limiter** that consumes `Vec<ExportedSpan>` from M6.4 and
produces `Vec<ExportedSpan>` back. No M6.4 modifications
beyond exposing `export_spans()` (the pre-render rich
structure).

### 2.1 Architecture

```
M6.4 export_spans()  ───────────►  Vec<ExportedSpan>
                                  │
                                  ▼
              M6.5 redact_and_limit_spans()
                                  │
                                  ▼
                              Vec<ExportedSpan>  (with redactions applied)
                                  │
                                  ▼
              M6.4 render_json_line()  ◄── M6.5::render_spans()
                                  │
                                  ▼
                              JSON Lines (stdout / OTLP)
```

The data flow is: rich spans → redacted spans → JSON.
M6.5 does **not** operate on the rendered JSON — it
operates on the rich span structures. This means M6.5
doesn't need a JSON parser, and redactions are applied at
the source of truth (the attribute value string).

### 2.2 RedactionPolicy

```rust
pub struct RedactionPolicy {
    pub sensitive_keys: Vec<String>,    // case-insensitive substring patterns
    pub redaction_marker: String,       // default "[REDACTED]"
}
```

Constructors:
- `RedactionPolicy::default_secrets()` — sensible defaults
  covering common secret-bearing keys (password, secret,
  token, api_key, auth, bearer, private_key, credential,
  credit_card, ssn, session_id, email).
- `RedactionPolicy::empty()` — disables redaction.
- `RedactionPolicy::with_keys(keys)` — custom keys.

`policy.matches(key)` returns true if the key (lowercased)
contains any of the sensitive substrings as a substring.

The redaction is **substring-based, case-insensitive**:
`Password`, `password`, `PASSWORD`, `api_key`, `apikey` all
match. This is more aggressive than exact-match but
intentionally so — secrets come in many forms.

### 2.3 CardinalityLimits

```rust
pub struct CardinalityLimits {
    pub max_distinct_keys: usize,        // default 64
    pub overflow_key: String,            // default "chronos._cardinality_collapsed"
}
```

- `max_distinct_keys` is the cap on **distinct** attribute
  keys across the entire export call (not per span).
- `overflow_key` is the shared key used when a key is
  collapsed. The value becomes `[cardinality-collapsed]`.
- Keys that match `RedactionPolicy` **do NOT count** toward
  the cardinality budget — they are removed from the
  distinct-keys set because their values become the marker.

### 2.4 Wire-format invariants

The redacted spans, when re-rendered through M6.4's
`render_json_line()`, produce JSON Lines where:

- Sensitive attributes have value `"[REDACTED]"` (or the
  configured marker).
- Sensitive attributes **keep their original key names** so
  downstream consumers can see *that* redaction happened
  for a given key (without seeing the secret).
- Overflow attributes are collapsed to the configured
  `overflow_key` with value `"[cardinality-collapsed]"`.
- All other fields (trace_id, span_id, name,
  start_time_unix_nano, chronos_invocation_id) are
  unchanged.

### 2.5 Determinism

`redact_and_limit_spans()` is a pure function (no I/O, no
time, no RNG). Given the same `Vec<ExportedSpan>` it
produces the same output and counters regardless of:
- input iteration order (counters are equal);
- platform (uses pure-Rust BTreeMap/BTreeSet).

Sensitive-key matching uses case-insensitive substring on
the literal key name; **no regex on the value** (no
regex-injection risk).

### 2.6 RedactionCounters

```rust
pub struct RedactionCounters {
    pub redacted_fields: usize,
    pub collapsed_cardinality: usize,
}
```

- `redacted_fields` — number of attribute values replaced
  with `[REDACTED]`.
- `collapsed_cardinality` — number of attribute values
  whose key was collapsed to `overflow_key`.

No silent drops: every redacted/collapsed value has a
counter.

## 3. Behavioural spec

### 3.1 Pipeline ordering

Redaction is applied **before** cardinality. This is by
design — sensitive keys are removed from the cardinality
budget so secrets don't "count" toward the cap.

Steps in `redact_and_limit_spans`:
1. **Pre-pass**: scan all spans, identify sensitive keys
   (do not count toward cardinality), identify distinct
   non-sensitive keys, mark which non-sensitive keys hit
   overflow.
2. **Apply pass**: for each attribute (key, value):
   - If `key` is sensitive → value becomes the marker;
     counter `redacted_fields++`.
   - Elif `key` is in overflow set → (key, value) becomes
     (overflow_key, "[cardinality-collapsed]"); counter
     `collapsed_cardinality++`.
   - Else → unchanged.

### 3.2 Empty policies

`RedactionPolicy::empty()` and `CardinalityLimits { max_distinct_keys: usize::MAX, ..default() }`
disable redaction and cardinality respectively. The pipeline
becomes a pass-through.

### 3.3 Zero cap

`CardinalityLimits { max_distinct_keys: 0 }` collapses
**every** non-sensitive key to `overflow_key`. This is the
strictest possible configuration and useful for testing.

### 3.4 Case-insensitivity

Redaction is case-insensitive on the key. Tested:
`Password`, `PASSWORD`, `API_KEY`, `apikey`, `api_KEY` all
match.

## 5. Why this matters for M6

M6.5 closes the **security/policy layer** between the
export pipeline and the network boundary. The two
policies (redaction + cardinality) were listed together in
ROADMAP because they're both pre-transmission gates on
sensitive/unbounded content.

- **M6.6 (UAT-M6-01/02)** spins two services and exports
  both. With M6.5 in place, the UAT can verify that
  secrets in attributes are redacted in the wire format.
- **M6.7 (gates)** verifies that round-trip
  `ingest → bind → export → redact → render` preserves
  correlation: a span exported from one service must be
  correlatable back to its origin via
  `chronos_invocation_id`, AND must not leak secrets.

The separation keeps M6.5 pure (no I/O, no
collection/network concerns) — the same way Google
Stackdriver Trace redaction sits between spans and the
collector.

## 6. Out-of-scope / future work

- **No value-pattern redaction**. M6.5 only redacts on
  key substrings. A future M6.x could add value-pattern
  redaction (e.g. SSN-shaped numbers) but that requires
  regex or a streaming pattern matcher and is out of
  scope here.
- **No encryption of redacted values**. The marker
  `[REDACTED]` is constant. Production would hash or
  truncate per-secret for forensics.
- **No tenant-scoped policies**. M6.5 has one global
  policy per call. Multi-tenant scoping requires per-tenant
  policy stacks.
- **No on-wire integrity**. The redacted span is just
  another JSON object. Production would sign spans before
  redaction (so the recipient can verify no redaction
  injection).
- **No per-tenant audit log**. Counter `redacted_fields`
  tells you *how many* redactions happened, not *which
  keys*. Production would log redaction events with the
  full key path.
- **No cardinality budget per key**. The cap is global to
  the export call. Production might want per-probe
  cardinality budgets.
