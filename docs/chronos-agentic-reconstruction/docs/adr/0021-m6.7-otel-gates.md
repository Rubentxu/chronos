**Status:** Accepted
**Date:** 2026-09-22
**Cycle:** M6 / M6.7 (gates de carga, recuperación y rutas de error del pipeline OTLP+redaction cross-service)
**chronos HEAD:** `e701776a` (post-M6.6 merge + STATE/JOURNAL alignment).
**Spike location:** off-repo, durable path `/home/rubentxu/m6-spikes/m6.7-otel-gates/`.

## 1. Context

ROADMAP §M6 §86 specifies seven sub-cycles M6.1..M6.7. M6.1..M6.6
deliver: tracing context (M6.1), OTLP adapter (M6.2), correlation
(M6.3), exporter (M6.4), redaction (M6.5), cross-service pipeline
(M6.6). M6.7 is the **final gate**: it exercises the assembled
pipeline under three adversarial conditions and proves the system
honours its acceptance contract end-to-end.

M6.6 closed the cross-service validation (UAT-M6-01 happy-path,
UAT-M6-02 adversarial-context). It does NOT prove that the pipeline
holds under sustained load, recovers from a downstream outage, or
degrades gracefully on malformed inputs. Those three conditions are
the operational reality that production telemetry demands.

M6.7 introduces three explicit gates that exercise the M6.6
`run_service_pipeline` contract plus M6.5's `RedactionPolicy` and
`CardinalityLimits` knobs:

- **Load gate** — N sequential pipeline calls; measure p50/p95/p99
  latency; verify the budget is honoured and zero events are
  dropped.
- **Recovery gate** — simulate `consumer` (downstream) UP→DOWN→UP
  cycle; verify that outages are *recorded* (not silently
  swallowed) and that idempotency over `trace_id` is preserved
  across the retry sequence.
- **Error paths gate** — feed empty/malformed/zero-events/extreme-
  cardinality inputs; verify the pipeline returns `Err(...)` or
  `Ok(0 spans)` deterministically and **never panics or invents
  provenance**.

The gates are deliberately independent: each one asserts a separate
invariant. A single aggregate runner (`run_all_gates`) executes all
three in sequence and emits a `GateReport` with per-gate verdicts.

## 2. Decision

**Accepted.** The M6.7 spike is implemented as a single library crate
`m6_7_otel_gates` with three public gate functions, three thin CLI
binaries, an end-to-end smoke example, and 13 contract tests.

### 2.2 The three gates

```rust
pub fn run_load_gate(
    n: usize,
    budget: &LoadBudget,
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> (Vec<LoadSample>, LoadGateVerdict);

pub fn run_recovery_gate(
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
    outage_at_start: bool,
    n_outage_requests: usize,
) -> (RecoveryState, RecoveryGateVerdict);

pub fn run_error_paths_gate(
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> (Vec<ErrorSample>, ErrorGateVerdict);

pub fn run_all_gates(
    n_load: usize,
    budget: &LoadBudget,
    n_outage_requests: usize,
    redaction: &RedactionPolicy,
    cardinality: &CardinalityLimits,
) -> GateReport;
```

### 2.3 Design constraints

| Constraint | Reason |
|---|---|
| No tokio / no async runtime | M6.6 chose stdlib HTTP + threads; this preserves the same deterministic synchronous model. |
| `Instant::now()` for p50/p95/p99 | Stdlib monotonic clock; no wall-clock, no invented Unix timestamps. |
| Outage is **logical**, not network-physical | `OutageState { consumer_up, service_b_up }` is a struct; the spike toggles it directly. This is testable, reproducible, and does not depend on the consumer TCP listener. |
| Idempotency measured over `trace_id` | M6.6 ADR §2.3 mandates this. Retries with the same `traceparent` map to the same `trace_id`; `RecoveryState.trace_to_invocations` tracks the *count* (idempotency holds ⇒ count == n). |
| Errors preserve provenance | `BadTraceparent { raw }` carries the original input; `OutageRecorded { target, since_micros }` carries the timestamp of the toggle. Never silently zero-ed. |
| Per-service redaction | M6.5 applies redaction per service; the gates consume the resulting `RenderedSpan` line, not raw OTLP. |

### 2.4 Verdict types

```rust
pub enum LoadGateVerdict { Pass, Fail { reason: String } }
pub enum RecoveryGateVerdict { Pass, Fail { reason: String } }
pub enum ErrorGateVerdict { Pass, Fail { reason: String } }
```

Each verdict is the only contract the gate exposes: a binary
pass/fail with a single human-readable reason. There is no
"warning" state — the gate either passes or it does not.

### 2.5 `GateReport` aggregator

```rust
pub struct GateReport {
    pub load: (LoadMetrics, LoadGateVerdict),
    pub recovery: (RecoveryState, RecoveryGateVerdict),
    pub error_paths: (ErrorGateVerdict, usize), // usize = sample count
}
```

`run_all_gates` executes the three gates sequentially, in the order
**load → recovery → error paths**, and returns the `GateReport`. This
ordering matters: load first (assumes a healthy system), then
recovery (toggles the consumer state), then error paths (independent
of consumer state). Running them in any other order would couple
their assumptions.

## 3. Alternatives considered

- **tokio + reqwest for HTTP load generation.** Rejected: M6.6
  chose stdlib HTTP; introducing tokio here would force the spike to
  depend on a different runtime than the M6.6 public API. Stdlib
  `Instant::now()` over N sequential calls is sufficient for the
  latency profile we need (microsecond granularity).
- **Real consumer TCP listener for outage simulation.** Rejected:
  requires the consumer to be running, introduces flakiness, and
  makes the gate dependent on a side-car process. The logical
  `OutageState` is testable, reproducible, and exercises the same
  contract branch.
- **Idempotency over `chronos_invocation_id`.** Rejected: M6.6 §2.3
  already mandated `trace_id`; re-keying here would contradict the
  previous ADR and weaken the contract. Re-confirmed in this ADR.
- **Per-gate separate crates (`m6_7_load`, `m6_7_recovery`,
  `m6_7_errors`).** Rejected: each gate alone is < 200 lines;
  splitting into three crates adds boilerplate (Cargo.toml ×3,
  bin/* ×3) without isolating any contract. One crate, three
  modules is the minimum sufficient.
- **Wall-clock timestamps in `OutageEvent`.** Rejected: per the
  global Chronos rule, no Unix timestamps in M6.* deliverables. The
  spike uses `Instant::now()` deltas, which are monotonic and
  portable.
- **Panic on malformed traceparent.** Rejected: the contract says
  errors must be returned, not panicked. `ErrorSample` carries the
  `Err(BadTraceparent { raw })` so the caller can inspect the
  original input.

## 4. Consequences

### Positive

- **Operational confidence.** Each gate is an executable
  specification of one acceptance criterion. Running them under CI
  tells us, in < 30 ms, whether the pipeline is healthy.
- **Independent testability.** The three gates are independent:
  one can fail without affecting the others. The aggregate verdict
  is the AND of the three.
- **Reproducibility.** No real network, no real consumer, no
  wall-clock. The same input produces the same output every time.
- **Audit-friendly.** `RecoveryState.outages: Vec<OutageEvent>`
  records *every* outage the spike exercised, with the monotonic
  timestamp. This is the receipt for the recovery gate.
- **Honest failure.** When a gate fails, the verdict's `reason`
  field is the exact invariant violated; nothing is hidden.

### Negative / costs

- **Logical outage vs. real outage.** The `OutageState` simulates
  the consumer being down without a real TCP disconnect. The M6.6
  pipeline branch *does* run; only the consumer-side `Ok`/`Err`
  path is exercised. A real consumer-down integration test would
  require a sidecar.
- **N=1000 may not be enough.** The smoke uses `n_load=1000` for
  speed. Production traffic would need higher N. The gate is
  parameterized over `n`; only the smoke default is small.
- **Single-thread sequential.** Concurrency in M6.6 used threads;
  this spike is single-threaded to keep the latency profile clean.
  Concurrent load will be a M7+ concern, not M6.7.

### Neutral

- **Three CLI binaries.** `load_runner`, `recovery_runner`,
  `error_runner` exist so each gate can be exercised
  independently. They share 95% of the code with the library;
  removing them would save ~ 100 lines total, but per-gate CLI
  invocation is the ergonomic shape for ops.

## 6. Mapping to UAT scenarios

| UAT scenario | How M6.7 covers it |
|---|---|
| UAT-M6-01 — happy-path cross-service | Already covered by M6.6 spike; M6.7 inherits the `run_service_pipeline` contract. |
| UAT-M6-02 — adversarial context | Already covered by M6.6; M6.7 *re-runs* it under load to confirm no regression. |

| UAT-M6-04 — recovery gate | `run_recovery_gate` — UP→DOWN→UP, idempotency over `trace_id`. Smoke proves 12 invocations / 1 trace_key ⇒ idempotency_holds=true. |

UAT-M6-03/04/05 are **new** M6.7 scenarios; they did not exist as
discrete items in the M6.1..M6.6 plan. They emerge from the M6.7
gate design and become part of the §M6 acceptance set.

## 7. M6 chapter close

M6.1..M6.7 are all closed. M6 is **7 / 7** complete. The cumulative
deliverable is an OTLP+redaction pipeline that:

- parses `traceparent` (M6.1, M6.2);
- correlates events with `trace_id` × `chronos_invocation_id` (M6.3);
- exports spans without inventing Unix timestamps (M6.4);
- redacts per-service with explicit cardinality caps (M6.5);
- correlates cross-service with two distinct `chronos_invocation_id`s
  per request (M6.6);
- and survives load, recovers from outage, and degrades gracefully
  on malformed inputs (M6.7).

The next chapter is M7 — differential execution v2.

## 8. Out-of-scope (explicit non-goals)

- **Async runtime.** All M6.* code is synchronous; bringing tokio
  in is a M8+ concern.
- **Persistent storage of gates output.** Verdicts are returned
  in-memory only; a metrics sink is a M10+ concern.
- **Concurrent load generation.** Single-threaded for clean
  latency profile; concurrency is a M7+ concern.
- **Real consumer outage.** `OutageState` is logical; a real
  consumer-down integration test is out of scope for M6.
- **Network partitions.** We model the consumer-down case only;
  partial network failure (split-brain) is a M11 OPS concern.
