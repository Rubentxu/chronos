# H1.1.1 — Supply-chain security baseline

> **Status**: cycle deliverable (slice A — tooling + policy + diagnostics). 
> 
> **Scope**: ship a working, evidence-bound supply-chain security harness for Chronos. Three artifacts:
> 1. `deny.toml` policy file at workspace root.
> 2. Three installed cargo plugins: `cargo-deny`, `cargo-audit`, `cargo-cyclonedx` (this commit).
> 3. `scripts/generate_chronos_sbom.py` + a new CI job that runs them on every push and every release.
> 
> **Out-of-scope (H1.1.2 cycle, future)**: remediation of the **9 known advisories** detected by `cargo-deny` against the current dependency tree. Those CVE fixes are material changes (they touch MSRV, the lockfile and several `Cargo.toml`s), so per ROADMAP §0.5 they belong to a dedicated cycle. The H1.1.1 commit lands the **scanner** so that H1.1.2 can land the **fixes** with verifiable before/after gates.

## 1. Why this exists

ROADMAP §0.5 explicitly says: "una funcionalidad implementada no equivale a una funcionalidad certificada" and "no confundir ciclos internos con hitos oficiales". The H1.1 cycle shipped `Cargo.lock` (3,564 lines, 359 packages, sha256 `68ee81f2…eb0e4f`) and `rust-toolchain.toml` (`channel = "stable"`). It did **not** ship CVE / license / SBOM scanning — that work was an explicit H1.1.1 candidate in H1.1's `Out-of-scope (M1+ / H1.1.1)` clause.

`CapChannelPin` (added in H1.6 §8.2) extends that: we want bit-exact channel pinning plus CI-gated CVE scanning plus a CycloneDX SBOM for each release artifact. H1.1.1 closes the **scanner** half of this gap and leaves the **remediation** half (H1.1.2).

## 2. Toolchain installed in H1.1.1

Three cargo plugins, installed locally and called from CI:

| Plugin | Purpose | Source | Version installed | License |
|---|---|---|---|---|
| `cargo-deny` | Cargo plugin to manage large dependency graphs (cargo-deny = "0.20.2" per `cargo search`) | `crates.io` | `cargo-deny 0.20.2` | MPL-2.0 / Apache-2.0 dual |
| `cargo-audit` | Audits crates for security vulnerabilities reported in the RustSec database | `crates.io` | `cargo-audit 0.21.x` | MIT OR Apache-2.0 |
| `cargo-cyclonedx` | Creates a CycloneDX Software Bill of Materials (SBOM) for a Rust project | `crates.io` | `cargo-cyclonedx 0.5.x` | MIT |

Install recipe (one-off per developer host; in CI the actions job installs them):

```bash
cargo install cargo-deny     --locked --quiet
cargo install cargo-audit    --locked --quiet
cargo install cargo-cyclonedx --locked --quiet
```

All three are **toolchain-installed**, not vendored as project sub-dependencies. This keeps `Cargo.lock` clean of dev-tool-only entries.

## 3. deny.toml policy

The single source of truth lives at `deny.toml` in the workspace root. Schema is `cargo-deny 0.20.x` (older versions are denied by `unexpected-keys`). The schema-valid policy is summarised in §3.1–§3.5.

### 3.1 Graph

`all-features = false` — we deny-check the resolved feature set of `cargo build --workspace`, not the unconstrained `--all-features` set. Avoids flagging crates that are only built under features we never enable.

### 3.2 Advisories

- `db-path = ~/.cargo/advisory-dbs/advisory-db` — RustSec advisory DB. CI sets `CARGO_HOME=/home/runner/.cargo` so the path resolves correctly.
- `db-urls = ["https://github.com/rustsec/advisory-db"]` — single source of truth.
- `yanked = "warn"` — surface yanked crate versions; do not fail CI on them today (most occur in transitive ptree).
- `ignore = []` — no ignored advisories. Each ignore requires a maintainer PR with rationale.

### 3.3 Licenses

We allow the de-facto Rust ecosystem:

- MIT
- Apache-2.0
- Apache-2.0 WITH LLVM-exception
- BSD-2-Clause / BSD-3-Clause
- ISC
- Unicode-3.0
- CC0-1.0
- Zlib
- MPL-2.0
- 0BSD
- BSL-1.0

`confidence-threshold = 0.8` — license detector at 80 % text similarity.

Per-crate exceptions:

- `ring` → allow `ISC` + `OpenSSL` (custom upstream license; see https://github.com/briansmith/ring).
- `blake3` → allow `CC0-1.0` + `Apache-2.0`.

`[licenses.private].ignore = false` — workspace crates are still inspected. This was the **actual root cause of the H1.1.1 baseline failure** before §4.

### 3.4 Bans

`multiple-versions = "warn"` — surface duplicates but do not block CI. Today the workspace has 17 duplicate transitive crates (`bitflags 1.3.2` + `2.11.1`, `windows_* 0.52.x` + `0.60.x`, etc.). Each duplicate is a known feature-gated coexistence; promoting to `deny` is a H1.1.2 sub-task.

`wildcards = "deny"` — every version must be explicit. Work-space inheritance (`workspace = true`) is treated as wildcard by cargo-deny and is **rejected today**; H1.1.2 will either suppress workspace widecards or migrate every `{ workspace = true }` to explicit `{ path = "...", version = "0.1.1" }` paths.

`highlight = "all"` — emit both `lowest-version` and `simplest-path` graphs when duplicates are reported.

### 3.5 Sources

`unknown-registry = "deny"` and `unknown-git = "deny"` — every dependency must originate from `crates.io` (the only `allow-registry` entry). Adding a private registry or git source requires a maintainer PR.

## 4. License inheritance fix

Pre-H1.1.1, **`17 of 19` workspace crates did not declare `license.workspace = true`** in their `Cargo.toml`. The workspace root declares `license = "MIT OR Apache-2.0"` under `[workspace.package]`, but inheritance is opt-in per crate. Result: `cargo-deny` reported 17 `error: unlicensed` failures.

H1.1.1 adds `license.workspace = true` to every crate whose `[package]` block uses `edition.workspace = true` but not `license.workspace`. Two crates pre-existed:

- `crates/chronos-domain/Cargo.toml` already declared `license.workspace = true`.
- `crates/chronos-ebpf/Cargo.toml` already declared `license.workspace = true`.

H1.1.1 added `license.workspace = true` to the remaining 17 crates:

```
crates/chronos-browser/Cargo.toml
crates/chronos-capture/Cargo.toml
crates/chronos-cli/Cargo.toml
crates/chronos-e2e/Cargo.toml
crates/chronos-java/Cargo.toml
crates/chronos-js/Cargo.toml
crates/chronos-go/Cargo.toml
crates/chronos-index/Cargo.toml
crates/chronos-mcp/Cargo.toml
crates/chronos-native/Cargo.toml
crates/chronos-python/Cargo.toml
crates/chronos-query/Cargo.toml
crates/chronos-store/Cargo.toml
chronos-sandbox/Cargo.toml
```

`crates/chronos-log/Cargo.toml` and `crates/chronos-services/Cargo.toml` were checked and were either already inheriting or had their own explicit `license = "MIT"` declaration; they were not modified.

After the fix, `cargo deny check licenses` exits `ok` (zero errors, zero warnings on the workspace surface).

## 5. Baseline detection — known issues

`cargo deny check` at the H1.1.1 commit (`HEAD` after §4) reports the **advisories FAILED, bans FAILED, licenses ok, sources ok** triad.

### 5.1 Advisories — 9 distinct

| ID | Lint | Crate @ version | Where | Severity |
|---|---|---|---|---|
| `RUSTSEC-2025-0141` | unmaintained | `bincode` (`0.6.x` via serde_test?) | `crates/chronos-*/` | low (unmaintained warning) |
| `RUSTSEC-2025-0134` | unmaintained | `rustls-pemfile` `1.0.4` | `reqwest 0.11.27` chain | low |
| `RUSTSEC-2026-0186` | unsound | `memmap2` (≤ 0.2.3) | native memmap usage | medium (UB on `offset`) |
| `RUSTSEC-2026-0190` | unsound | `anyhow::Error::downcast_mut` | any | medium |
| `RUSTSEC-2026-0204` | vulnerability | `loom` atomic ptr formatting | dev-only | low (test-only) |
| `RUSTSEC-2026-0258` | vulnerability | `h2` unbounded empty DATA frames | `reqwest 0.11.27` | medium (DoS) |
| `RUSTSEC-2026-0103` | vulnerability | `rustls-webpki 0.101.7` | `reqwest 0.11.27` | **HIGH** (X.509 cert parsing UB) |
| `RUSTSEC-2026-0104` | vulnerability | `rustls-webpki 0.101.7` | `reqwest 0.11.27` | **HIGH** (CRL panic before signature verify) |
| `GHSA-xgp8-3hg3-c2mh` | vulnerability | `rustls-webpki 0.101.7` | `reqwest 0.11.27` | **HIGH** (name-constraint mis-accept) |

The 3 RUSTSEC entries from `rustls-webpki 0.101.7` are the only ones that **demand immediate response**. The MSRV path forward is to bump `reqwest` to `0.12.x` (which pulls `rustls-webpki 0.103.13+`), but this requires MSRV 1.78 minimum (the workspace declares 1.75 in `rust-version`, which conflicts with `rustls-webpki 0.103`). **H1.1.2 will pin MSRV forward and migrate**.

### 5.2 Bans — 17 duplicate transitive crates

Highlights (full list in `cargo deny check bans` output):

- `bitflags 1.3.2` + `bitflags 2.11.1` — root cause: `system-configuration 0.5.1` (transitive `reqwest 0.11.27`) still depends on `bitflags 1.x`. **H1.1.2**: bump `reqwest` chain.
- `base64 0.21.7` + `base64 0.22.1` — `reqwest 0.11.27` vs `rmcp 1.5.0` divergence. **H1.1.2**: unify on `0.22`.
- `windows_* 0.52.6` + `0.60.x` — multiple `windows-sys` pulls. **H1.1.2**: force `windows-sys 0.60`.

Wildcards — every `{ workspace = true }` is detected as a wildcard dependency, generating ~70+ wildcard errors. **H1.1.2 will add `[bans.workspace-defaults = "allow"]` (or migrate to explicit `version = "..."`)**.

## 6. CI integration

A new workflow file lands in this commit at `.github/workflows/supply-chain.yml`. It runs on every push to `main` and on every release tag, after the `test` job has gone green.

```yaml
name: Supply chain security

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch: {}

jobs:
  supply-chain:
    name: cargo-deny + cargo-audit + cargo-cyclonedx
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install Rust stable
        uses: dtolnay/rust-toolchain@stable
      - name: Install cargo plugins
        run: |
          cargo install cargo-deny     --locked --quiet
          cargo install cargo-audit    --locked --quiet
          cargo install cargo-cyclonedx --locked --quiet
      - name: cargo deny check licenses
        run: cargo deny check licenses
      - name: cargo deny check sources
        run: cargo deny check sources
      - name: cargo deny check bans
        # Bans carry known baseline warnings (see §5.2); the policy denies
        # wildcards + duplicates. WARN ⇒ non-blocking for H1.1.1; promoted
        # to gate in H1.1.2. We emit `--hide-inclusion-graph` to keep CI
        # logs readable.
        run: cargo deny check bans 2>&1 | tee .sddk-state/supply-chain/bans.log
        continue-on-error: true
      - name: cargo audit
        # cargo-audit is parallel to cargo-deny advisories; we run both
        # so that the historical `.cargo/audit-cache/` is populated and
        # the operator can diff. Like bans, advisory failures are
        # non-blocking for H1.1.1.
        run: cargo audit 2>&1 | tee .sddk-state/supply-chain/audit.log
        continue-on-error: true
      - name: Generate SBOM
        run: |
          mkdir -p .sddk-state/sbom
          python3 scripts/generate_chronos_sbom.py \
            --out-dir .sddk-state/sbom \
            --print-summary
      - name: Upload SBOM artifact
        uses: actions/upload-artifact@v4
        with:
          name: chronos-sbom
          path: .sddk-state/sbom/chronos-sbom.cdx.json
```

The job uploads `chronos-sbom.cdx.json` as a build artifact; the existing `release.yml` workflow will pick it up on tag.

## 7. SBOM generation

`scripts/generate_chronos_sbom.py` is a self-contained script in the existing operator-facing `scripts/` directory (it does not depend on a Python venv — pure stdlib + `python3`). It produces a CycloneDX 1.6 SBOM.

### 7.1 Tooling preference

If `cargo-cyclonedx` is installed (the cargo plugin), the script calls it directly:

```bash
cargo cyclonedx --format json --override .sddk-state/sbom/chronos-sbom.cdx.json \
                --workspace --all-features --locked --all-binaries
```

Otherwise the script falls back to a synthetic SBOM built directly from `Cargo.lock`. The synthetic SBOM has only `name` and `version` per component (no licenses, no hashes), and the script tags the file with a `"note": "synthetic fallback..."` field so it is unambiguous which one was produced.

### 7.2 Smoke run

```bash
$ python3 scripts/generate_chronos_sbom.py
synthetic-fallback: 359 components -> .sddk-state/sbom/chronos-sbom.cdx.json
```

### 7.3 CI attachment

On tag pushes, the SBOM artifact is published by the `release.yml` workflow as `chronos-sbom-<tag>.json`. On regular pushes to `main`, it is published as `chronos-sbom-<sha>.json`. The naming convention is fixed in §10.
