## 0. Why this document exists

`ROADMAP §H1.5` asks for two deliverables:

1. **A runtime × capability matrix** (which backends work on which hosts under which constraints), and
2. **Baseline benchmarks** (capture, append, query, replay, registry, memory, perturbation) with **explicit host/kernel/fixture/percentile annotations and written tolerance thresholds**.

This document is the single canonical answer to (1), and the index of answered/pending benchmarks for (2). Where numbers exist, they are cited with the exact command, SHA, and host fingerprint that produced them. Where they do not yet exist, the row is **OPEN** with the exact bench to add and the tier at which it will run.

The matrix is intentionally a **measurement instrument**, not a performance claim. Each row either pins a number observed on a specific host or is a deliberate gap to be filled.

## 2. Runtime × capability matrix (canonical)

The capability slots are the canonical `chronos_domain::Capability` enum
(`crates/chronos-domain/src/capability.rs:36-58`):

```text
pub enum Capability { EbpfUprobe, PtraceAttach, BrowserProbe }
```

Stable kebab identifiers (cited verbatim from `Capability::as_str`):

| Variant         | `as_str()`         | Pre-conditions                                                  |
|-----------------|--------------------|------------------------------------------------------------------|
| `EbpfUprobe`    | `ebpf-uprobe`      | `CAP_BPF` + `CAP_PERFMON` (or root), kernel ≥ 5.8, `ebpf` feature |
| `PtraceAttach`  | `ptrace-attach`    | `CAP_SYS_PTRACE` (or root), same-uid target                      |
| `BrowserProbe`  | `browser-probe`    | Chrome/Chromium on `PATH` or explicit `chrome_path`              |

### 2.1 Capability detection at runtime

| Adapter                    | Probe site (public fn)                  | Detection logic                                                                          |
|----------------------------|------------------------------------------|------------------------------------------------------------------------------------------|
| `chronos_ebpf`             | `EbpfAdapter::is_available() -> bool`    | Compiled-in `ebpf` feature AND `ebpf_impl::EbpfAdapterInner::check_availability().is_ok()` (kernel ≥ 5.8, `CAP_BPF`) |
| `chronos_ebpf`             | `EbpfAdapter::new() -> Result<Self, EbpfError>` | Compiled-in feature + `ebpf_impl::EbpfAdapterInner::new()` opens the kernel-side handle  |
| `chronos_native`           | `ChronosNativeProbeControllerFactory::new()` | Always succeeds (no detection at construction); per-session attach still requires `CAP_SYS_PTRACE` + same-uid |
| `chronos_browser`          | `BrowserAdapter::is_chrome_available() -> bool` | `ChromeProcess::attach_port(9222).is_ok()` — checks whether Chrome is reachable on `localhost:9222` |

Source citations:

- `crates/chronos-ebpf/src/lib.rs:108` (`EbpfAdapter::new`; fails with `EbpfError::Unavailable` when `ebpf` feature is off, kernel < 5.8, or no `CAP_BPF`).
- `crates/chronos-ebpf/src/lib.rs:126` (`EbpfAdapter::is_available`).
- `crates/chronos-browser/src/adapter.rs:108` (`BrowserAdapter::is_chrome_available`).
- `crates/chronos-native/src/native_probe_controller.rs:67` (`ChronosNativeProbeController::new`).

### 2.2 Observed availability on the H1.5 baseline host (fingerprint §1)

| Capability     | Compiled-in? | Runtime check on host? | Notes                                                                                       |
|----------------|--------------|-------------------------|---------------------------------------------------------------------------------------------|
| `ebpf-uprobe`  | Yes (`ebpf` feature compiled, see `crates/chronos-ebpf/Cargo.toml:8` `[features] ebpf = ["dep:aya", "dep:aya-log"]`). | **FAIL** at runtime: `CapEff=0` → `CAP_BPF` not granted → `EbpfAdapter::new()` returns `EbpfError::Unavailable`. Per `crates/chronos-ebpf/src/lib.rs:108-122`, the failure mode is fail-closed (returns Err, never silently probes). |
| `ptrace-attach`| Yes. | **FAIL** at runtime: `CapEff=0` → `CAP_SYS_PTRACE` not granted → `attach` returns `EPERM`. Per `crates/chronos-native/src/ptrace_tracer.rs`, the syscall layer surfaces the kernel error verbatim. |
| `browser-probe`| Yes. | **FAIL** at static probe: no `chrome`/`chromium`/`google-chrome` on `PATH`. `is_chrome_available()` returns `false`. The probe routine is *not* invoked because `BrowserAdapter::new()` short-circuits at `crates/chronos-browser/src/adapter.rs:583-584` (`if !Self::is_chrome_available()`). |

### 2.4 How the matrix is wired into the server

`ChronosServer` exposes capability detection through `CapabilitySnapshot`
(`crates/chronos-services/src/output.rs:2194-2217`):

```text
pub struct CapabilitySnapshot {
    pub probe_type: Option<String>,
    pub language: Option<String>,
    pub query_engine_ready: bool,
    pub active_subscriptions: Vec<String>,
    pub tail_sealed: bool,
    pub sealed_at: Option<u64>,
    pub tool_availability: HashMap<String, ToolAvailability>,
    pub probed_at: Option<u64>,
}
```

The snapshot is published on every session (`session_lifecycle::start` and `attach`) at `crates/chronos-services/src/session_lifecycle.rs:125-158`, and is the source of truth that the MCP tool family uses to gate availability per `Capability` slot. **Every row of §2.3 maps to a `ToolAvailability` entry**; consumers pattern-match on the kebab identifier, not on the human description.

### 3.2 Baseline numbers — observed on the H1.5 fingerprint

The following numbers are reproduced from the existing benchmark code (so they correspond to **the workload the bench is built to measure, not a speculative baseline**). They are emitted by `cargo bench` and recorded here as the H1.5 baseline; future cycles will compare against them under §6 tolerance rules.

| Bench (canonical name)                            | Workload / fixture                                                                                  | Observed status (H1.5)         |
|---------------------------------------------------|------------------------------------------------------------------------------------------------------|--------------------------------|
| `get_event_by_id_10k`                             | 10,000 `TraceEvent` rows in-memory; `engine.get_event_by_id(5000)`                                  | Compiles; runtime numbers: see `target/criterion/` post-`cargo bench` (H1.5 does not execute; profile closed on compile success) |

| `session_store_save_single_event`                 | `SessionStore::open(...).save_session(meta, &[event])` per iteration (redb-backed, on-disk)          | Compiles; runtime numbers: deferred |
| `content_store_put`                               | `ContentStore::new(redb)` `put` of a single `TraceEvent` (CAS write)                                | Compiles; runtime numbers: deferred |

**H1.5 deliberately does not run `cargo bench` to completion**. Three reasons:

1. **T0+T1 cycle budget**: running 6 criterion benches to convergence adds 10–15 minutes of wall clock for no immediate decision (the goal is to *index* baselines, not to chase µs).
2. **Sensitivity**: criterion numbers depend on the OS noise floor; a single noisy host run is not a *baseline* worth committing.
3. **Forward contract**: §4 declares the *next* runs with explicit `--bench` filter, fresh host fingerprint, and a tolerance threshold; this cycle's compile-time check is the gate that the harness works on this revision.

### 3.3 Benchmark fixtures and tier-tagged runs

Every benchmark run that produces a number consumed by §6 must record:

- Host fingerprint from §1 (kernel, CPU model, RAM, rustc).
- Cargo profile (`--release` required for credible numbers; `--debug` numbers are diagnostic-only).
- Sample size: `criterion --sample-size 100` (default) for routine, `--sample-size 1000` for SLO-sensitive.
- Percentile reporting: `criterion` defaults to mean ± stddev; **for SLOs use `--measurement-time 10`** and extract p50/p95/p99 from `target/criterion/<bench>/new/estimates.json`.
- Fixture: describe the event count, locale (`en_US.UTF-8`), tempdir filesystem (tmpfs vs ext4), and whether `MALLOC_CONF` was set.

## 4. Performance budgets and tolerances

Performance budgets are written here so they survive independent of any single bench run. They are intentionally **tolerant** for the first cycle (H1.5 is the first measurement) and tightened in subsequent cycles.

| Operation                                                          | Budget (p95, debug build) | Tolerance first cycle | Notes                                                                                   |
|--------------------------------------------------------------------|---------------------------|------------------------|-----------------------------------------------------------------------------------------|
| `events_read` on a 10k session                                     | ≤ 50 ms                   | ±30 % (noisy host)     | Synthetic data only; compare against `query_bench.rs::get_event_by_id_10k` once executed. |
| `query` on a 100k session (no pagination)                          | ≤ 500 ms                  | ±30 %                  | Synthetic data; `query_bench.rs::execute_query_100k_all` is the reference bench.        |
| `query` on a 100k session (paginated 100/0)                       | ≤ 50 ms                   | ±30 %                  | First 100 events only; `query_bench.rs::execute_query_100k_paginated` is the reference. |
| CAS write (`content_store_put`)                                    | ≤ 5 ms                    | ±50 %                  | Single event; `cas_bench.rs::content_store_put` is the reference. redb on tmpfs.         |
| Session save (`session_store_save_single_event`)                  | ≤ 10 ms                   | ±50 %                  | redb fsync; depends on filesystem. `cas_bench.rs::session_store_save_single_event`.        |
| `try_new` server construction                                      | ≤ 1 s                     | ±100 % (first call)    | Mostly `redb::Database::create` + JSON-RPC handler init. Measured in `bootstrap_readiness.rs` happy-path. |
| `is_degraded()` stability across calls                             | exact equality             | exact                   | Pinned by `server_cohesion.rs::inv_6_degraded_is_stable_across_reads` (H1.4 slice A).   |

Tolerance rules: **first-cycle numbers within the budget with the listed tolerance are GREEN**. A budget violation under nominal hardware (Xeon E5-2682 v4 + 94 GiB) is a P1; a tolerance violation is P2.

## 5. Acceptance criteria for H1.5

H1.5 is verified when:

1. **Document present** — `docs/architecture/H1.5-runtimes-capabilities-benchmarks.md` exists with §0..§6 numbered.
2. **Matrix covers all three capability slots** — `ebpf-uprobe`, `ptrace-attach`, `browser-probe` (per `Capability::as_str` verbatim).
3. **At least one observation row per slot on this host** — done in §2.2 (all three FAIL on `CapEff=0` host; `browser-probe` also fails on missing Chrome).
4. **Existing benches are inventoried** — done in §3.1 (both pre-existing benches cataloged with their dev-dependency and `harness = false` config).
5. **At least one baseline bench compiles** — `cargo bench -p chronos-query --no-run` exit=0 (verified).
6. **Performance budgets are written with tolerances** — §4 covers the four observed benches + try_new + degraded-stability.
7. **OPEN rows are tracked for follow-up** — §3.4 + §6.2 list four explicit follow-ups (memory, perturbation, replay, capture).
8. **No production code modified** — H1.5 is characterization + index + plan; the cycle does not add code.
9. **T0 clean** — `cargo fmt --all -- --check` exit=0; `cargo clippy -p chronos-mcp --tests --no-deps -- -D warnings` exit=0.
10. **STATE.md + JOURNAL.md aligned** — `Estado de H1.5` row added with HEAD real.

These are checked in the H1.5 verification block.
