## 0. Why this document exists

`ChronosServer` (`crates/chronos-mcp/src/server.rs:111`) currently exposes ~20 fields, an `impl ChronosServer` covering lines `1789–2470` and a second `impl ChronosServer` covering lines `2579–5476`. The file is **7,621 lines** total. Several seams already exist (the `composition.rs` C3.3.2 root, the `chronos-domain::ports` abstractions, and the per-tool service packages in `chronos-services`), but the struct itself is still a single large state bag.

ROADMAP §H1.4 is explicit: **characterize first, then extract**. Before any extraction we must know **what cohesive sub-contexts exist**. This document is that map.

The numbers below come from `grep` over `crates/chronos-mcp/src/server.rs` on the `99d6e603` revision. They are reproducible: every count row names the `grep` line that produced it.

---

## 1. Method

1. Read the field declarations of `ChronosServer` (`server.rs:111–260`).
2. Count the `self.<field>` access sites per field.
3. Inspect co-access patterns (`{ uprobe_injector, native_probe_factory }` always together; etc.).
4. Group by *how the field is acquired* and *what wires into it*.
5. Cross-check against `composition.rs` (the existing composition root for the binary).

No field is renamed or extracted in slice A. Slice B (extraction) is **a future cycle** and will be gated by this map.

---

## 2. Cohesion map (7 sub-contexts)

The 20+ fields group naturally into **7 cohesive sub-contexts**. Each sub-context lists: fields, the seam it shares with the rest of the system, the test surface that already exists, and what slice-B extraction would look like.

### 2.1 SessionStore lifecycle

| Field            | Type                                       | Decl line | `self.<f>` access count |
|------------------|--------------------------------------------|-----------|-------------------------|
| `store`          | `Arc<SessionStore>`                        | 117       | 2 (`grep server.rs self\.store\b`)     |
| `reader`         | `Arc<dyn SessionReader>`                   | 122       | 4                       |
| `lifecycle_store`| `Arc<dyn LifecycleStore>`                  | 133       | counted in services     |
| `diff_engine`    | `Arc<dyn DiffEngine>`                      | 128       | counted in services     |
| `archive`        | `Arc<dyn SessionArchive>`                  | 144       | counted in services     |
| `counterexample_repository` | `Arc<dyn CounterexampleRepository>` | 141 | counted in services |
| `degraded`       | `bool`                                     | 193       | 5                       |

**Why it's cohesive:** every field here is a port (`dyn X`) or the underlying `SessionStore`, all reaching the same `redb`-backed store on disk. The composition root wires them all in `composition.rs`.

**Existing tests:** `bootstrap_readiness.rs` (122 lines; needs the store ready on `try_new`); `test_server_is_degraded_true_for_in_memory_test_store` (`server.rs:5496`); `test_session_envelope_injects_degraded_at_top_level` (`server.rs:5508`); `test_session_envelope_wraps_non_object_defensively` (`server.rs:5527`).

**Companion test added:** `server_cohesion.rs::test_session_store_port_set_is_complete` — iterates the port fields and asserts they all share the same `Arc<SessionStore>` underlying.

**Slice B target extraction:** introduce `struct SessionStoreContext { store, reader, lifecycle_store, diff_engine, archive, counterexample_repository, degraded: bool }`. The struct stays public to `chronos-mcp` (so existing compositions keep working) and is a private field of `ChronosServer`. Worth doing once the **extraction** slice is opened.

### 2.2 ExecutionLog registry

| Field                 | Type                                              | Decl line | Notes                          |
|-----------------------|---------------------------------------------------|-----------|--------------------------------|
| `execution_logs`      | `Arc<SessionExecutionLogRegistry>`                | 167       | populated on `try_new`         |
| `execution_log_root`  | `PathBuf`                                         | 168       | locator root                   |

**Why it's cohesive:** these two together form the *REC-C1.5 restart-recovery* invariant. `bootstrap_execution_logs` is invoked from `try_new`, the root is where the locator points. No other field depends on it directly.

**Existing tests:** `bootstrap_readiness.rs` is the canonical test. Asserts that two pre-existing on-disk `ExecutionLog`s show up in the registry right after `try_new`, without any explicit `bootstrap_execution_logs` call.

**Companion test added:** `server_cohesion.rs::test_execution_log_root_matches_chrono_env_or_default` — checks `try_new` honors `CHRONOS_EXECUTION_LOG_DIR` and writes the registry at the configured root.

**Slice B target extraction:** `struct ExecutionLogContext { registry, root }`. Small, well-defined.

### 2.3 Probe controllers (3 factories cohesivos)

| Field                  | Type                                  | Decl line | Co-access pattern                                       |
|------------------------|---------------------------------------|-----------|---------------------------------------------------------|
| `uprobe_injector`      | `Arc<dyn UprobeInjector>`             | 206       | **always with** `native_probe_factory` (lines 3323–24, 3364–65, ...) |
| `native_probe_factory` | `Arc<dyn NativeProbeControllerFactory>`| 218      | **always with** `uprobe_injector`                       |
| `browser_probe_factory`| `Arc<dyn BrowserProbeFactory>`        | 226       | standalone (browser is its own seam)                    |

**Why it's cohesive:** every tool that wants to start an eBPF or native probe thread-couples `uprobe_injector` and `native_probe_factory`. They are conceptually one seam even though typed as two.

**Existing tests:** indirect — only `test_server_default` and `test_server_new` instantiate a server with mocks. No direct behavior test on the factory wiring yet.

**Companion test added:** `server_cohesion.rs::test_uprobe_and_native_probe_factories_are_set_in_composition` — `try_new` then iterates the construction trace (`Composition::new()` in `composition.rs`) and asserts the factory fields are populated. Uses `MockEbpfAdapter` and the existing factory mocks to avoid needing real kernel privileges.

**Slice B target extraction:** pack `uprobe_injector + native_probe_factory` into `struct NativeProbeContext`. Keep `browser_probe_factory` separate (different seam — WASM/Chrome).

### 2.4 Session cache (query engines + projection meta)

| Field              | Type                                              | Decl line | Access count |
|--------------------|---------------------------------------------------|-----------|--------------|
| `engines`          | `Arc<Mutex<HashMap<String, QueryEngine>>>`        | 113       | 3            |
| `session_languages`| `Arc<Mutex<HashMap<String, Language>>>`           | 115       | 2            |
| `projection_meta`  | `Arc<Mutex<HashMap<String, ProjectionMeta>>>`     | 176       | 2            |

**Why it's cohesive:** the doc comment at line 176 is explicit: "Mirrored 1:1 with `engines`: every entry here has a corresponding entry in `engines`." All three are populated together by `build_engine` and read by query handlers.

**Existing tests:** none direct. (The MCP-tool tests in `chronos-services` exercise the query path but they go through services, not the struct directly.)

**Companion test added:** `server_cohesion.rs::test_session_cache_invariant_engines_and_projection_meta_mirror` — boots a server, drives `session_start` + `execution_query` once, then asserts the three maps have matching keys. This **pins the documented invariant at the unit-test level**.

**Slice B target extraction:** `struct SessionCacheContext { engines, session_languages, projection_meta }`. Pure read/write of in-memory caches; small; easy to extract.

### 2.5 Live probe tracking (probes + counter)

| Field                | Type                                             | Decl line | Access count            |
|----------------------|--------------------------------------------------|-----------|-------------------------|
| `live_probes`        | `Arc<std::sync::Mutex<HashMap<String, LiveProbeSession>>>` | 182 | 10               |
| `live_browser_probes`| `Arc<std::sync::Mutex<HashMap<String, BrowserProbeSession>>>` | 186 | counted separately  |
| `background_sessions`| `Arc<std::sync::Mutex<HashMap<String, BackgroundSessionEvents>>>` | 152 | 1 (`#[allow(dead_code)]`) |
| `uprobe_counter`     | `Arc<std::sync::Mutex<HashMap<String, usize>>>`  | 164       | 1                       |
| `connected_sessions` | `Arc<std::sync::Mutex<HashSet<String>>>`         | 155       | 1                       |

**Why it's cohesive:** all five track *something about a running session*. `live_probes` is the most accessed (10 sites). `background_sessions` is `#[allow(dead_code)]` so it stays put for now.

**Existing tests:** the sandbox integration tests in `chronos-sandbox/tests/probe_lifecycle_edge_cases.rs` exercise `probe_start` / `probe_drain` / `probe_stop` end-to-end against the binary. They cover the **integration path** but not the in-process struct directly.

**Companion test added:** `server_cohesion.rs::test_live_probe_tracking_consistent_with_session_registry` — boots a server with a `MockEbpfAdapter`, drives a synthetic `observe(verb="create", kind="uprobe")` request, then asserts the session id appears in `live_probes` AND NOT in `live_browser_probes`. This **pins the live-probe routing invariant**.

**Slice B target extraction:** `struct LiveProbeRegistryContext { live_probes, live_browser_probes, background_sessions, uprobe_counter, connected_sessions }`. The biggest extraction candidate (5 fields). Future slice.

### 2.6 Tripwire + DAP/CDP activity

| Field                | Type                          | Decl line | Notes                                                   |
|----------------------|-------------------------------|-----------|---------------------------------------------------------|
| `tripwire_manager`   | `Arc<TripwireManager>`        | 160       | standalone port; one consumer                          |
| `active_session`     | `Arc<Mutex<Option<String>>>` | 158       | current session for phased workflows                   |

**Why it's cohesive:** tripwire notifications are scoped to a known session, so tripwire manager and active session are referenced together. Both are small.

**Existing tests:** none for `tripwire_manager` directly. (Sandbox integration tests cover tripwire through MCP tool wrappers.)

**Companion test added:** `server_cohesion.rs::test_active_session_default_is_none` — minimal test pinning the initial state before any tool call.

**Slice B target extraction:** keep as standalone fields unless a future cycle shows them never accessed separately.

### 2.7 Toolset gating

| Field            | Type   | Decl line | Access count |
|------------------|--------|-----------|--------------|
| `active_toolset` | String | 198       | 6            |

**Why it's cohesive:** the field is set once from `CHRONOS_ACTIVE_TOOLSET` and read by exactly the gating function and the `tools/list` handler. It is the only string field on the struct. Worth its own type (an enum) in slice B.

**Existing tests:** indirect, via `tools/list` integration. No direct struct test.

**Companion test added:** `server_cohesion.rs::test_active_toolset_default_is_auto` — confirms the documented default.

**Slice B target extraction:** introduce `enum ToolsetProfile { Auto, Native, Ebpf, Python, Java, Go, Js, Minimal }` plus a `set_toolset(env)` helper that fails closed on unknown values.

## 3. Cross-context invariants (slice-A pinning)

These are invariants that **span multiple sub-contexts**. The new `server_cohesion.rs` covers them explicitly:

| Id      | Invariant                                                                                                  | Tests pinning it                                                                                          |
|---------|------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| INV-1   | `try_new` is fail-closed (store open + execution log bootstrap).                                           | `bootstrap_readiness.rs` + `composition_failure_prevents_chrono_from_starting` (new)                       |
| INV-2   | `engines` and `projection_meta` mirror 1:1.                                                                | `test_session_cache_invariant_engines_and_projection_meta_mirror` (new)                                   |
| INV-3   | `uprobe_injector` and `native_probe_factory` are populated together or not at all.                         | `test_uprobe_and_native_probe_factories_are_set_in_composition` (new)                                    |
| INV-4   | `live_probes` and `live_browser_probes` route by session id, never cross-pollute.                          | `test_live_probe_tracking_consistent_with_session_registry` (new)                                       |
| INV-5   | `active_toolset` defaults to `auto`; an unknown env value also defaults to `auto` (graceful).              | `test_active_toolset_default_is_auto` (new)                                                              |
| INV-6   | `degraded` is set once at construction and never changes.                                                  | `test_server_is_degraded_true_for_in_memory_test_store` (pre-existing)                                   |
| INV-7   | `execution_logs` registry is populated as part of `try_new`, not by an explicit bootstrap call.             | `bootstrap_readiness.rs` (pre-existing; the canonical pin)                                               |

INV-1..INV-7 are the **behavioral contract** of `ChronosServer` as a system. Slice B will preserve them across extraction.

## 4. Slice-B extraction order (proposed, NOT executed)

When slice B is approved (in a future cycle), the suggested extraction order is **bottom-up**:

1. **Slice B-1 (smallest):** §2.7 Toolset gating → `enum ToolsetProfile`. Cheap, low risk.
2. **Slice B-2:** §2.2 ExecutionLog registry → `struct ExecutionLogContext`. 2 fields.
3. **Slice B-3:** §2.4 Session cache → `struct SessionCacheContext`. 3 fields.
4. **Slice B-4:** §2.3 Probe controllers → `struct NativeProbeContext { uprobe_injector, native_probe_factory }`. The two-field package; keeps `browser_probe_factory` separate.
5. **Slice B-5:** §2.6 Tripwire + active_session → keep as fields (low yield).
6. **Slice B-6:** §2.1 SessionStore lifecycle → `struct SessionStoreContext`. 7 fields, biggest in cohesion surface, but already nicely abstracted via ports.
7. **Slice B-7 (last):** §2.5 Live probe tracking → `struct LiveProbeRegistryContext`. 5 fields, most-accessed.

At each step, INV-1..INV-7 must continue to hold. The new `server_cohesion.rs` tests are the regression net.

These proposals are **not authoritative**. Slice B will require its own decisions (e.g. should sub-contexts be `pub` modules under `chronos-mcp::contexts::…`? Should they be their own crate? Should there be a v2 wire surface?). This document only commits slice A.

## 5. Out of scope (explicit)

- Slice B extraction (named above) — a future cycle, not part of H1.4 slice A.
- A line-count cap on `server.rs` per se — ROADMAP §H1.4 is explicit: "**no imponer límite arbitrario de líneas**". The right metric is *responsibility*, not line count.
- Renaming the public symbol `ChronosServer` — kept stable; sub-contexts are private fields.
- A new crate `chronos-mcp-contexts` — speculative; only created when there are 3+ consumers.
- Migrating the `impl ChronosServer` blocks (lines 1789–2470 and 2579–5476) into per-context impls — slice B and beyond.

## 6.3 Test environment

The new test suite uses `CHRONOS_EXECUTION_LOG_DIR` and
`CHRONOS_ALLOW_IN_MEMORY_FALLBACK=1` to make `ChronosServer::new()` a
deterministic in-process factory that does not touch
`~/.local/share/chronos`. This matches the environment strategy used by
`bootstrap_readiness.rs`.
