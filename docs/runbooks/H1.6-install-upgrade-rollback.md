## 1. Deployment profiles

Chronos is **local-first and stdio-bound today**. The four deployment profiles in H1.2 §4.1–§4.3 have very different feature and capability support. Operators must pick the profile that matches their actual deployment; the binary does NOT auto-detect profile.

### 1.1 `local/stdio` — LOCAL-ONLY, STDIO-MCP (VERIFIED)

| Field | Value |
|---|---|
| State | **VERIFIED** post-G0 (regression check at `903c72ef`: `cargo test -p chronos-mcp --test server_cohesion` = 9/9 PASS in 2.76 s) |
| Transport | JSON-RPC over stdin/stdout (`--stdio` flag, default in `Dockerfile`) |
| Persistence | File-backed redb at `$CHRONOS_DB_PATH` (default: `$CWD/chronos-data/sessions.redb`) |
| Process model | 1 process = 1 MCP server = 1 store |
| Multi-tenancy | NO (single operator owns the host filesystem) |
| Network exposure | NO (server never opens a port) |
| Capabilities observed on baseline host | `CapEff=0000000000000000` → all 3 capability slots (`ebpf-upprobe`, `ptrace-attach`, `browser-probe`) fail closed. `BrowserProbe` additionally fails on no-Chrome-on-PATH. See H1.5 §2.2. |
| Source references | `crates/chronos-mcp/src/bin/chronos-mcp.rs:24-34` (`try_new` fail-closed), `crates/chronos-services/src/output.rs:2193-2212` (`CapabilitySnapshot` struct) |

**When to use this profile**: dev, CI, single-user debugging, sandbox suite like `chronos-sandbox/`. **Cannot** be used as a shared service.

### 1.2 `local/network` — NOT IMPLEMENTED

| Field | Value |
|---|---|
| State | **NOT IMPLEMENTED** |
| Reason | `chronos-mcp` server is wired for `--stdio` only; no `axum`/`hyper` listener exists in `crates/chronos-mcp/src/bin/`. |
| Source references | H1.2 §4.3 row "local/network". |
| Required for | `capability → network-transport` (M1+). |

### 1.3 `Linux privileged` — NOT IMPLEMENTED (operator-side)

| Field | Value |
|---|---|
| State | **NOT IMPLEMENTED** (operator-side requirements only) |
| What operators must do today if they want eBPF capture | Run with `setcap cap_bpf,cap_sys_ptrace+ep` and have a `vmlinux` BTF file in `/sys/kernel/btf/vmlinux` (Linux ≥ 5.8) |
| What operators must NOT do today | Run as `root` blindly. The server does NOT elevate. See H1.5 §2.2 baseline-host observation |
| Source references | H1.2 §4.2; H1.5 §2.1 (`EbpfAdapter::is_available`). |

### 1.4 `remote/multi-tenant` — NOT IMPLEMENTED

| Field | Value |
|---|---|
| State | **NOT IMPLEMENTED** |
| Reason | No transport, no auth, no per-session isolation. H1.2 §4.3. |
| Required for | `CapAuth`, `CapRedact`, `CapMultiTenant` (M1+). |

> **Operator rule**: today, the only deployable profile is §1.1. Every other profile is documented for completeness so future engineers know what is **NOT** shipping in H1.x and why.

## 2. Install matrix

Each install method covers a specific subset of the binary surface. The workspace emits exactly **two binaries** today (`crates/chronos-mcp/Cargo.toml`, `crates/chronos-cli/Cargo.toml`):

| Binary | Crate | Role |
|---|---|---|
| `chronos-mcp` | `chronos-mcp` | MCP server entrypoint (stdin/stdout JSON-RPC) |
| `chronos` | `chronos-cli` | Operator CLI (replay, inspect, export) |

### 2.1 Method A — `cargo install` from a release tag

Pre-built `Cargo.lock` is the only source of reproducible bit-identical builds for the supported toolchain. The current stable tag is `v0.7.112` (peel at `0be2ec2d`). Required toolchain: `rustc 1.98.1` (this host's stable at H1.1 close), supplied via `channel = "stable"` in `rust-toolchain.toml` (see H1.1).

```bash
# 1. Pin the toolchain (H1.1)
rustup toolchain install 1.98.1 --profile minimal
rustup toolchain link default 1.98.1  # optional, recommended

# 2. Build the MCP server (release profile)
git checkout v0.7.112
cargo build -p chronos-mcp --release
# Output: target/release/chronos-mcp

# 3. Build the CLI
cargo build -p chronos-cli --release
# Output: target/release/chronos

# 4. Optional: cargo install into ~/.cargo/bin
cargo install --path crates/chronos-mcp --locked --profile release
cargo install --path crates/chronos-cli --locked --profile release
```

### 2.2 Method B — container (Docker / docker-compose)

The repository ships `Dockerfile` (multi-stage `rust:1.77-slim` builder → `debian:bookworm-slim` runtime) and `docker-compose.yml`. There is **one** known pre-existing drift: the builder uses `rust:1.77` (H1.x pre-pinning era). The build succeeds with `--locked` because `Cargo.lock` is committed.

```bash
docker compose build chronos-mcp    # uses docker-compose.yml
docker compose up -d chronos-mcp    # starts with --stdio, RUST_LOG=info
docker compose down                 # stops, retains volume
```

The compose service is wired for STDIO MCP only (§1.1). Networking, env-based DB override, and persistent volume `chronos-data` (mapped to `/data/chronos/`) are honored.

> **Operator rule**: if the operator is on the Docker path, **Method B is the canonical install**. Method A inside the container is unnecessary.

### 2.3 Method C — prebuilt GitHub release artifact (NOT YET PUBLISHED)

> **GAP — `CapPrebuiltArtifact` (M1+)**. The release pipeline does not publish prebuilt binaries for Linux/macOS/Windows. Until it does, only Method A and B are reachable. Source reference: H1.2 OPS.7 row ("No remote-update mechanism").

When H1.6 cycle ships, the SHA verification path is in §3.2 below — it is staged but not yet exercised end-to-end because Method C artifacts do not exist.

### 2.4 Method D — dev / from source

For developers hacking on Chronos itself:

```bash
git clone https://github.com/Rubentxu/chronos
cd chronos
rustup toolchain install 1.98.1
cargo build -p chronos-mcp       # debug profile, fast iteration
cargo test --workspace --lib --no-fail-fast
```

The `cargo build` step at workspace root compiles **all** binaries, including every backend probe adapter (`chronos-native`, `chronos-tracing`, etc.). Use `-p` to scope to one binary.

## 3. Artifact verification

H1.1 pinned `channel = "stable"` via `rust-toolchain.toml`. Operators today see `rustc 1.98.1` on recent hosts, but the lockfile floats with `stable` (no bit-exact minor pin yet — see `CapChannelPin` M1+). The verification chain is **four** layers. Each layer is independent; failing one does not invalidate the others, but failing several raises confidence concerns.

### 3.1 Layer 1 — `Cargo.lock` SHA

The committed `Cargo.lock` is the only lockfile. `cargo install --locked` and `cargo build --locked` reject drift. Operators can verify the lockfile is what the maintainers recorded:

```bash
sha256sum Cargo.lock
# Compare to the value recorded in docs/roadmap/STATE.md (cell "Lockfile hash")
```

The current pinned hash is recorded in `STATE.md` under "Lockfile hash".

### 3.2 Layer 2 — release tag + peel

The release tag `v0.7.112` peels to a single commit `0be2ec2d`; the tag is intact and signed with the maintainer's GPG key (operationally, the `git rev-parse <tag>^{}` must equal the commit the maintainers pinned):

```bash
git rev-parse v0.7.112^{}
# Expected: 0be2ec2d53d9698956ae705938b32b80d7365ad7
git cat-file -e 0be2ec2d && echo "SHA valid"
```

### 3.3 Layer 3 — binary SHA-256 (after build)

Once built (Method A or B inside container), capture the binary fingerprint:

```bash
sha256sum target/release/chronos-mcp target/release/chronos
```

Today no published fingerprint database exists (depends on Method C, see §2.3). **Operators must record these locally** for their own audit trail. When Method C ships, the maintainer-recorded fingerprint will live at `docs/releases/<tag>/sha256sums.txt`.

### 3.4 Layer 4 — runtime smoke

After install, run a minimal smoke against the server. This is the same wire-smoke pattern that G0 closed:

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"0"}}}' \
  | target/release/chronos-mcp --stdio
# Expected: one JSON line with capabilities.serverInfo.version
```

Today, no automated script exists in `scripts/` for this exact wire-smoke. The reproducer scripts that G0 added live in `cycle-artifacts/p-3416cfb8288f8964/` and should not be copied to `scripts/` (they belong to the cycle, not the operator-facing surface).

## 4. Upgrade paths

Four upgrade scenario classes. The principle: **upgrade the binary, verify the schema compat window, restart, smoke**. There is no in-place binary update — operators ship a new binary and switch the symlink (or restart the container).

### 4.1 Patch upgrade (x.y.Z, Z+1 — backward-compatible fix)

| Step | Action |
|---|---|
| 1 | Read release notes; confirm no schema change (`schema_version` unchanged) |
| 2 | Capture binary SHA-256 (§3.3) of old binary; copy to backup |
| 3 | `git checkout v<new-tag>` (e.g. v0.7.113) |
| 4 | `cargo install --path crates/chronos-mcp --locked --profile release` |
| 5 | Verify binary SHA-256 and `cargo lock` show no drift |
| 6 | Stop server, swap binary, restart |
| 7 | Smoke (§3.4) |
| 8 | Rollback if smoke fails (see §5.1) |

### 4.2 Minor upgrade (x.Y+1.0 — backward-compatible feature)

Same shape as patch, with one extra rule: **schema version is allowed to add (read-compat) but not change**. See §6.2 for the schema-version compatibility window.

### 4.3 Major upgrade (X+1.0.0 — schema-bumping)

Requires a **schema migration run** first. Today, **no migration tooling exists** (it is the `CapExport` M1+ gap). The rule today is:

- Pre-flight: read release notes; confirm a migration path is documented
- If no migration is documented, **do NOT upgrade**. Stay on the old major.

### 4.4 Canary upgrade (operator-only, reversible)

For operators who want to test a new tag without committing:

| Step | Action |
|---|---|
| 1 | `git checkout v<new-tag>` in a separate worktree |
| 2 | Build a canary binary in that worktree |
| 3 | Run canary binary against a **copy** of `$CHRONOS_DB_PATH` (not the live store) |
| 4 | Verify wire-smoke (§3.4) and spot-check replay output |
| 5 | Discard the worktree |

Canary requires no infrastructure change. The clone-of-store is a manual `cp -a $CHRONOS_DB_PATH /tmp/canary-redb`.

## 5. Rollback paths

Three rollback scenario classes. Each is documented as a discrete recipe because the failure mode is different.

### 5.1 Known-bad upgrade (binary works, semantic regression)

| Step | Action |
|---|---|
| 1 | Stop the failing server |
| 2 | Restore previous binary from backup (§3.3) |
| 3 | Restore previous `Cargo.lock` from `git checkout <old-tag>^ -- Cargo.lock` (optional; only if lockfile drift matters) |
| 4 | Restart with `--stdio` |
| 5 | Smoke (§3.4) |
| 6 | Confirm old behavior |

Schema is **not affected** because the known-bad upgrade uses the same schema version.

### 5.2 Data corruption (binary cannot read its own store)

Today, this triggers `try_new` fail-closed at `ContentStore::try_new`. The store refuses to open if `schema_version` mismatches the binary's expectation. Recovery is to roll back to the binary that wrote the store:

| Step | Action |
|---|---|
| 1 | Do NOT modify the store directory manually |
| 2 | Identify last known-good `schema_version` (1 today; see §6.1) |
| 3 | `git checkout` the tag recorded for that schema version |
| 4 | Rebuild, swap binary |
| 5 | Verify server boots against the existing store |
| 6 | Export the store (`CapExport` is M1+ — today, operators `cp -a` the directory) |

### 5.3 Capability loss (post-upgrade, eBPF/ptrace/browser slots stop binding)

Typically caused by environment change, NOT by the upgrade — but operators may blame the binary. Triage is:

| Step | Action |
|---|---|
| 1 | Run `capsh --print` to confirm `CapEff` |
| 2 | Check `/sys/kernel/btf/vmlinux` exists (eBPF) |
| 3 | Check `CHRONOS_REQUIRE_<CAPABILITY>` env vars in operator config |
| 4 | Run server with `RUST_LOG=chronos_mcp=debug,chronos_domain=debug` to see the `CapabilitySnapshot` log |
| 5 | If snapshot regressed, bisect by rebuilding old binary and re-checking |

Reference: `crates/chronos-services/src/output.rs:2193-2212` (snapshot type), `crates/chronos-mcp/src/bin/chronos-mcp.rs:24-34` (`try_new` fail-closed startup).

## 6. Schema-version compatibility

The store schema version is asserted explicitly. `chronos-cli/replay.rs` writes `schema_version: 1` at ten sites (line numbers 284, 294, 398, 405, 448, 468, 496, 516, 548, 559) plus two more in `chronos-mcp/composition.rs` (414, 421), defaults in `chronos-domain/ports/counterexample/mod.rs` (lines 82-89, 116 via `default_schema_version`), and test fixtures in `chronos-store/ce_storage_tests.rs`. `chronos-store::ContentStore::try_new` (`crates/chronos-store/src/`) refuses to open a store with a mismatched schema version; see H1.2 OPS.5 row.

### 6.1 Current schema version

`schema_version = 1`. This is hardcoded at **16 sites** across `crates/`: `crates/chronos-cli/src/replay.rs` (10 sites at lines 284, 294, 398, 405, 448, 468, 496, 516, 548, 559), `crates/chronos-mcp/src/composition.rs` (2 sites at lines 414, 421), `crates/chronos-domain/src/ports/counterexample/mod.rs` (defaults via `default_schema_version` at lines 82-89, 116), and `crates/chronos-store/src/ce_storage_tests.rs` (test fixtures). There is no constant table; a schema bump would mean editing all sites coherently and adding a migration. **Do not edit those lines without consulting the maintainers.**

### 6.2 Compatibility window

| Binary version → Store schema | 1 | 2 (future) |
|---|---|---|
| Binary version N reads schema 1 | OK (current) | NO (try_new fail-closed) |
| Binary version N+1 reads schema 1 | OK (read-compat) | OK (current) |

The matrix is intentionally minimal. Multi-version support and automated migration are `CapExport` (M1+).

### 6.3 Operator rule

If `try_new` fails with a schema-version mismatch, the operator MUST roll back to the binary version that wrote the store (§5.2). The server never silently coerces.

## 7. Support and diagnostics

All current observability is via `tracing-subscriber::EnvFilter` to `stderr`. Operators can configure verbosity without code changes.

### 7.1 Logs

```bash
RUST_LOG=info ./chronos-mcp --stdio   # default
RUST_LOG=debug ./chronos-mcp --stdio  # verbose
RUST_LOG=chronos_mcp=debug,chronos_domain=info ./chronos-mcp --stdio
```

### 7.2 Reproduction recipe (a "support bundle")

To file an effective issue, operators should attach:

1. `uname -a` (kernel)
2. `rustc --version` (track `rustc 1.98.1` today; the lockfile is `channel = "stable"` so this may drift — recording is the point)
3. `cargo --version`
4. `cat Cargo.lock | sha256sum` (lockfile hash, must match STATE.md "Lockfile hash": `68ee81f2…eb0e4f`)
5. `git rev-parse HEAD` (HEAD of `chronos` repo at issue time)
6. `capsh --print | grep CapBnd,CapEff` (effective capability set)
7. `./chronos-mcp --version` (binary version)
8. `sha256sum <binary>` (binary fingerprint)
9. The minimal repro command and the JSON-RPC payload that triggered the issue
10. Last 50 lines of stderr with `RUST_LOG=debug`

`CapTraceArchive` (structured tracing export) is M1+. Today logs are stderr-only.

### 7.3 Wire-level diagnostics

The server is wired for STDIO MCP only. There is no network listener and no health probe. **Every** operator call must come through JSON-RPC over stdin. A direct `nc 127.0.0.1 3000` connection will fail (no socket is bound). This is a feature, not a bug: §1.1.
