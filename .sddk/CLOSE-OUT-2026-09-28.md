## Open item 5 — the watched dependency set is incomplete

**Severity: the guard has a hole.** `mcp_dependency_sources` in
`chronos-sandbox/src/client/tools.rs` watches a hand-written list of 8 crate names. The real
transitive workspace closure of `chronos-mcp` is **13** crates. Five are unwatched:

`chronos-native`, `chronos-python`, `chronos-js`, `chronos-ebpf`, `chronos-browser`.

Observed via `cargo metadata --format-version=1`, traversing `resolve.nodes[].deps` from the
`chronos-mcp` node and intersecting with `workspace_members`. Not inferred from `Cargo.toml` text,
because `Cargo.toml` only shows direct dependencies and the closure also picks up transitive members.

Consequence, stated precisely: a stale binary is still accepted when the only edit since the last
build is inside one of those five crates. The guard is proven against the mutation that motivated it
(`chronos-services`) and against a first-version bug (`chronos-mcp` only). It is **not** proven
exhaustive, and this entry is the reason not to describe it as such.

The fix is to derive the set from `cargo metadata` instead of maintaining it by hand, which also
removes the drift risk permanently. Cost is bounded: `cargo metadata` measured at ~1.5 s, and
`assert_fresh` runs once per binary resolution, not per test. Not started, because the suite was still
running against the tree when this was found, and mutating a source under a live run is exactly what
produced three false failures earlier in the session.

## What I got wrong, recorded so it is not repeated

I first claimed the cause was fixture exhaustion: the captured `test_busyloop`
dies at ~3s and the test's own `sleep(2s)` consumed its life, so the second

**A mutation test refuted it.** Swapping the fixture to `test_infinite_loop`
was supposed to be the fix; swapping it back to `test_busyloop`, changing
nothing else, still advanced the cursor (seq 2 -> 15, 34ms). So the busyloop
is not exhausted when the wait runs. The arithmetic was real and the causal
claim was wrong.

I also wrote and then **reverted** a 300s -> 60s deadline reduction, because it
rested on that refuted cause. Commit `5fea8f1b` carries the revert.

## Refuted, so not re-tried blindly

- **Fixture exhaustion** — see above.
- **CPU contention** — 48 spinners on 64 cores: first event 5ms -> 164ms, but
  the advance still lands inside the deadline. Load slows it, does not break it.
- **ptrace slowdown** — `strace -f -c`: 3.06s vs 3.01s native. Negligible.
- **Deadline length** — five prior bumps (10/30/60/120/300) each expired at
  ratio ~1.0x. That is a state arriving late, not a state never arriving.
